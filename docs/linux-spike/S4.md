# S4: move_frame then move_resize_frame, at scale 1 and 1.5, on two monitors

Spike S4 of the Linux Tiler (docs/linux-tiler/wayfinder.md §5, M0b row 5). It feeds settling, the D1 seam and M1b.

## Question

`move_frame` then `move_resize_frame` on GTK4, libadwaita, Electron, Ghostty and Xwayland (`xterm`): how long until
the frame settles, and what size it reaches (cell-sized terminals), at scale 1 and 1.5, with `scale-monitor-framebuffer`
and `xwayland-native-scaling`, on two monitors with the primary at x=2560. Do headless virtual monitors accept scale
1.5, or does the L1 runner need `ApplyMonitorsConfig`?

## Answer

- **The two experimental features don't exist in mutter 50.1.** Fractional scaling (the logical layout) and native
  Xwayland scaling are always on; the owner's `experimental-features` value only produces two "Unknown experimental
  feature" warnings. With a 1.5 monitor, every X11 client lives in a 2x X11 space on both monitors (X11 scale =
  ceil of the highest monitor scale).
- **Headless virtual monitors accept 1.5**, if the mode divides by it (3840x2160 does, 2560x1440 doesn't). Both ways
  work: a `monitors.xml` in the throwaway `XDG_CONFIG_HOME` is applied at startup, and `ApplyMonitorsConfig` (method
  1, temporary) on the private bus applies in 48-166 ms. Without either, mutter puts the first monitor at (0,0) as
  primary at scale 1, so a config is always needed for the owner's layout. **The L1 runner should write
  `monitors.xml`**: no D-Bus step, and the layout is right before the first frame.
- **Wayland clients (GTK4, libadwaita, Ghostty) reach the exact rect, at both scales**, after one size change.
  `move_frame` moves them at once; `move_resize_frame` sends a configure, and the size lands at the client's commit:
  medians 120-180 ms on the scale-1 monitor and 190-1000 ms on the 1.5 one, worst 1.5 s, at L1 (software
  rendering, host load 21-45). Ghostty doesn't snap to cells on
  Wayland; it pads inside the rect it gets.
- **Xwayland `xterm` is synchronous** (the frame is set in the call) and **snaps down to its resize increments**:
  never larger than asked, short by less than one increment per axis (seen: up to 8x16 px at scale 1, 4x6 px at
  1.5 for a 9x18 cell). At scale 1.5 mutter rounds the increments to whole stage pixels (4.5 to 5), so the window is
  not a whole number of cells.
- **`move_frame` first is needed across monitors, for every client.** `move_resize_frame` alone, from the primary to
  the other monitor, left `xterm` on the primary (resized only), and clamped every GTK client to the *primary's* work
  area height (1048 instead of 1420): the configure carried the primary's `configure_bounds`.
- **Two requests for one window in quick succession can lose the newer one.** A late ack of the older configure puts
  the window back at the older rect. Within one monitor the newer rect follows; across the primary/non-primary
  boundary, with `workspaces-only-on-primary=true` (the owner's setting), mutter then re-configures the window to the
  older rect and the newer request is dropped for good: 8 of 18 cross-monitor requests with 20-150 ms between them, in
  GTK4, libadwaita and Ghostty alike. With the setting false: 0 of 18.

## What it decides

**Engineering defaults (M1b settling):**

1. Every tiling move is `move_frame(true, x, y)` then `move_resize_frame(true, x, y, w, h)`, for Wayland and X11
   alike. `move_resize_frame` alone is never used for a move between monitors.
2. **One request in flight per window.** The backend keeps, per window, the newest rect it asked for. A newer rect for
   a window whose previous request hasn't settled is held and sent after the settle (or sent at once and re-asserted
   after it); after each settle, a frame that differs from the newest request and equals an older request is re-sent
   once. The utwm-style "achieved frame fed back" must not report a reverted rect as what the client chose.
3. **The settle rule:** a request has settled at the first `size-changed` (or at once, if the size didn't change), plus
   a short quiet period; the achieved frame is what vase gets back. Tolerance: Wayland windows reach the exact rect;
   X11 windows with increments may be short by less than one increment per axis, never larger. The L1 settle timeout
   is 2 s (worst seen 1.5 s under llvmpipe and load); the desktop's number comes from the L3 feel check, not from here.
4. **X11 scale is global:** on the owner's desktop X11 windows on the scale-1 primary are also in the 2x X11 space.
   The Tiler works in stage (logical) pixels only and never converts X11 geometry itself.

**For the map:**

- F11 needs a line: in 50.1 `scale-monitor-framebuffer` and `xwayland-native-scaling` are not features any more
  (mutter NEWS 50.beta, "Make VRR and fractional scaling non-experimental", !4863, !4877); the owner's setting is
  inert. The row-5 wording ("with `scale-monitor-framebuffer` and `xwayland-native-scaling`") describes 50.1's only
  behaviour.
- `gnome-api.md` §4.2's prior-art note ("some terminals only resize and don't move") is wider than terminals: across
  monitors, every client needs `move_frame` first (above).
- D1 is unchanged: `Main.layoutManager.primaryIndex` follows the config (index 1 at x=2560 here), so the backend can
  report the primary; nothing in S4 argues for another source.
- The L1 runner for M1b: its own launcher, not `gnome-shell-test-tool` (which always adds one 1280x720 virtual
  monitor, `/usr/bin/gnome-shell-test-tool:91`); two `--virtual-monitor` options; `monitors.xml` in the throwaway
  config dir; `SHELL_BACKGROUND_IMAGE` set as the test tool sets it; and a startup watchdog (below).
- **No owner question.** `workspaces-only-on-primary` stays as it is: rule 2 above handles the dropped request.

**Nothing here blocks the architecture.** The lost request is a settling detail the backend owns (rule 2); it is a
compositor behaviour to know, not a missing capability.

## Method

Level L1 only: a headless GNOME Shell 50.1 inside rootless podman, never on the host.

- **Image:** `chained-tiler-s4`, built from `chained-tiler-test:0f162fbd9318eba8` (the M0a image, gnome-shell
  50.1-0ubuntu1.5, libmutter-18-0 50.1-0ubuntu2.5, the host's versions) plus xterm 407-1ubuntu1,
  libadwaita-1-examples 1.9.1 (`adwaita-1-demo`), ghostty 1.3.0~us1 and x11-utils, from the same archive snapshot
  (`spikes/S4/Containerfile`). GTK4 is `gtk4-demo` (gtk 4.22.4). **Electron is not covered:** the Ubuntu archive has
  no Electron app, and the container has no network for a download.
- **Runner** (`spikes/S4/l1.sh`, then `run.sh` inside): `--rm`, `--cap-drop=all`, `no-new-privileges`,
  `--network=none`, `--ulimit core=1:1` (no apport report for a crash), the checkout read-only, `nice -n 19`, and a
  wait while the 1-minute load is over 40. Inside: `dbus-run-session` plus the M0a `dbusrunner.py` (mocked system
  bus), `GSETTINGS_BACKEND=keyfile` in a throwaway home with the owner's `experimental-features` and
  `workspaces-only-on-primary=true`, then `gnome-shell --headless --virtual-monitor 3840x2160 --virtual-monitor
  1920x1080 --automation-script spikes/S4/s4.js`.
- **Layouts:** `xml15` (monitors.xml: Meta-0 3840x2160 at scale 1.5 at (0,0), Meta-1 1920x1080 at scale 1 at
  (2560,0), primary), `dbus15` (no monitors.xml; the script calls `ApplyMonitorsConfig` for the same layout), `xml1`
  (Meta-0 2560x1440 at scale 1, the primary again at x=2560).
- **Per client** (`s4.js`): spawn, wait for the window and its first frame, then a series of requests, each
  `move_frame(true, …)` then `move_resize_frame(true, …)` to rects built from the work areas with odd sizes and
  offsets: both halves of the primary, the other monitor's left half and an odd quarter, back to the primary, then
  `move_resize_frame` alone across monitors, then two requests back to back (0 ms, and in later runs 20, 60, 150 and
  400 ms apart, across and within monitors). Every `size-changed` and `position-changed` is timestamped; a request has
  settled after 2 s (later runs 4 s and 8 s) with no change. "Settled at" is the first time the frame reached its
  final rect.
- **Protocol trace:** one run with `WAYLAND_DEBUG=1` on the clients (configure, `configure_bounds`, `ack_configure`,
  commit).
- **Sources:** mutter 50.1 from `download.gnome.org` (sha256 `9344502c…021e`, matches the published sum) with
  Ubuntu's 37 patches from `mutter_50.1-0ubuntu2.5.debian.tar.xz` applied (all applied cleanly); line numbers below
  are of that patched tree. No patch touches the code cited.
- **Host check:** `tools/before-after.sh` snapshots at 04:58:21 and 06:34:04: no watched item changed.

Timings are L1 numbers: llvmpipe software rendering of a 3840x2160 plus a 1920x1080 stage, on a host at load 21-45
shared with other jobs. They bound the desktop's numbers from above and show the order of events; they are not the
owner's latency.

## Evidence

Raw `[s4]` lines of each run are in `spikes/S4/evidence/` (`python3 -I spikes/S4/summarize.py FILE` prints the
tables, `--stats FILE...` the settle statistics).

### 1. The experimental features are gone in 50.1

- `src/backends/meta-settings.c:47-50`: the only experimental features are `kms-modifiers` and
  `autoclose-xwayland`; anything else logs `Unknown experimental feature '%s'` (`:311`). Every run's log has both
  warnings, as S11's L3 log did.
- `src/backends/native/meta-monitor-manager-native.c:483-486`: the native backend's default layout mode is
  `LOGICAL`, unconditionally (it used to depend on `scale-monitor-framebuffer`).
- `src/wayland/meta-xwayland.c:1350-1376`: in the logical layout the Xwayland scale is
  `xwayland-scaling-factor` if set, else `ceil(highest_monitor_scale)` over all monitors (`:1061-1081`).
  Measured: X11 root 8960x2880 on a 4480x1440 stage at scale 1.5 (X11 scale 2), 4480x1440 at scale 1.
- Ubuntu ships the old value as a default (`/usr/share/glib-2.0/schemas/10_mutter-common.gschema.override`,
  `[org.gnome.mutter:GNOME] experimental-features=['scale-monitor-framebuffer', 'xwayland-native-scaling']`).
- mutter NEWS, 50.beta (`NEWS:109`): "Make VRR and fractional scaling non-experimental [!4863, !4877]".

### 2. Virtual monitors and scale 1.5

- `--virtual-monitor WxH[@R]` takes no scale (`src/core/meta-context-main.c:309-343`); each monitor is vendor
  `MetaVendor`, product `MetaVirtualMonitor`, serial `0x00`, `0x01`, …, connectors `Meta-0`, `Meta-1`. A virtual
  monitor has no physical size, so its default scale is 1 (`src/backends/meta-monitor.c:2372`).
- **Default layout** (`GetCurrentState` at start, no config): Meta-0 at (0,0) scale 1 **primary**, Meta-1 at
  (3840,0). Supported scales: 3840x2160 `[1, 1.25, 1.333, 1.5, 1.667, 2, 2.5, 2.667, 3, 3.333, 3.75, 4]`,
  1920x1080 `[1, 1.25, 1.333, 1.5, 1.667, 2]`, **2560x1440 `[1, 1.25, 1.333, 1.667, 2, 2.5, 2.667]` (no 1.5)**:
  only scales that divide the mode evenly (`meta-monitor.c`, `for_each_scale`).
- **monitors.xml** in `$XDG_CONFIG_HOME` (`src/backends/meta-monitor-config-store.c:2867`) is matched by connector,
  vendor, product and serial and applied at startup: `Meta-0 at 0,0 scale 1.5; Meta-1 at 2560,0 scale 1 primary`,
  `primaryIndex 1`, stage 4480x1440, work areas (0,0 2560x1440) and (2560,32 1920x1048) (top bar on the primary
  only). Same for the scale-1 layout.
- **ApplyMonitorsConfig** (method 1, layout-mode 1) from the automation script, asynchronously (the shell answers
  `org.gnome.Mutter.DisplayConfig` itself): accepted, `monitors-changed` 166 ms and 48 ms later in two runs, same
  result as monitors.xml. The handler only refuses on a stale serial or a config store policy with D-Bus disabled
  (`src/backends/meta-monitor-manager.c:2926-2962`).
- The X11 display policy is MANDATORY in the container (no systemd user unit, `meta-context-main.c:136-153`), so
  Xwayland runs from the start.

The slowest request is often the first one after the window mapped (libadwaita 629-844 ms, Ghostty about 1 s, on
the primary). On the 1.5 monitor GTK4 and Ghostty are slower: INFERENCE, their buffers there are 1.5x larger in each
direction, and the clients render in software. Neither scale changes the size reached.

What happens in each call (read back right after it):

- After `move_frame`, a Wayland window is already at the new position with its old size: a pure move sends no
  configure and moves at once (`src/wayland/meta-window-wayland.c:330-366`, `should_configure`, then
  `can_move_now`).
- After `move_resize_frame`, the position stays and the size is unchanged until the client commits; at the commit the
  position is recomputed from the acked configuration (`meta-window-wayland.c:1718`, `calculate_position
  (acked_configuration, …)`), here the same position.
- For `xterm`, both calls take effect in the call: `meta_window_x11_move_resize_internal` sets the frame
  (`src/x11/window-x11.c:1299`) and sends `XConfigureWindow`; `size-changed` fires within 0.1-15 ms.

### 4. The cell-sized terminal

`xterm -fa 'DejaVu Sans Mono' -fs 11`: `WM_NORMAL_HINTS` resize increment 9x18, base 4x4 (X pixels); `-fs 22`
(standing in for the `Xft.dpi 192` gsd-xsettings sets on the desktop when X11 scale is 2): 18x35.

- Mutter converts the hints to stage pixels with `MTK_ROUNDING_STRATEGY_ROUND` (`src/x11/window-props.c:1284-1287`)
  and snaps the client size down to `base + n * increment` (`src/core/constraints.c:1492-1560`).
- Scale 1 (X11 scale 1): 954x1040 asked, 949x1033 reached (frame = client + 39 px titlebar: (950 mod 9) = 5 px and
  (997 mod 18) = 7 px cut). Shortfalls seen: up to 8x16 (`-fs 11`) and 17x34 (`-fs 22`).
- Scale 1.5 (X11 scale 2): increments 4.5x9 become 5x9 stage pixels, 17.5 becomes 18; shortfalls up to 4x6 and
  7x13. The real cell is 4.5 stage pixels wide, so mutter's 5-pixel steps leave up to a cell of padding in xterm.
- Never larger than asked, and nothing changes after the call (one `size-changed`).

### 5. `move_resize_frame` alone, from the primary to the other monitor

Target (10,10 1260x1420) on the 1.5 monitor, from the primary:

- GTK4, libadwaita, Ghostty: frame at (10,10) but **1260x1048** in every run, at both scales. The trace
  (`evidence/trace-adw-mrf-only-to-other.txt`): mutter sent `configure_bounds(1920, 1048)` (the primary's work area,
  `meta_window_calculate_bounds`, `src/core/window.c:8346-8369`, uses the window's current main monitor) with
  `configure(1260, 1420)`; the client set its geometry to 1260x1048. Once on the new monitor, mutter sent
  `configure_bounds(2560, 1440)` with the current 1260x1048, and it stayed there.
- xterm: **not moved**, resized to the target size on the primary (final x 3521, y 33). This is the case Tiling
  Assistant works around (`gnome-api.md` §4.2).
- With `move_frame` first, the window is on the target monitor before the configure, and every client reaches the
  rect (section 3).

### 6. Two requests in quick succession

Request A, then request B for the same window, each `move_frame` + `move_resize_frame`.

- **0 ms apart** (`overlap-*` in xml15, xml1, dbus15): the window shows A's position for the fraction of a millisecond
  between the two `move_frame` calls, then B; one size change, B reached. No problem.
- **20-400 ms apart** (`delays15`, `trace15`, `woop-*`): when A's configure is acked after B was requested, the window
  jumps back to A's rect (A's acked configuration carries A's position).
  - Within one monitor: B's ack follows and B is reached (12 transient jump-backs in 36 requests, 0 lost).
  - Across the primary/non-primary boundary, with `workspaces-only-on-primary=true`: **B is lost**. The window stays
    at A's rect, with no further change for the whole quiet period (2, 4 or 8 s): 7 of 24 (`delays15`), 7 of 12
    (`trace15`), 8 of 18 (`woop-true`). GTK4, libadwaita and Ghostty all show it.
  - The same runs with `workspaces-only-on-primary=false` (`woop-false`): 0 of 18 lost, 4 transient jump-backs.
- **The trace** (`evidence/trace-adw-overlap-20ms-primary-then-other.txt`, libadwaita, A on the primary, B on the 1.5
  monitor 20 ms later): `configure(956, 524)` serial 14 with the primary's bounds, acked and committed; B's
  `configure(1276, 1436)` serial 15 with bounds 2560x1440; then, 16 ms later, **a third `configure(956, 524)` serial
  16 with the primary's bounds again**, which the client acked and committed. Serial 15 never got a commit of its own.
- **Why** (INFERENCE from the source, consistent with the trace and with the on/off result): the late commit of serial
  14 moves the window back to the primary. Its acked configuration is floating, so the unconstrained rect becomes A's
  (`meta-window-wayland.c:659-665`). Crossing to the primary flips `on_all_workspaces` under
  `workspaces-only-on-primary` (`window.c:4446-4458`, `5475-5496`), and `set_workspace_state` queues a move-resize
  (`window.c:5442-5446`), which re-applies the unconstrained rect, A (`meta_window_idle_move_resize`,
  `window.c:4951-4970`), as a new configure, serial 16. Acking 16 discards 15, since the acked serial drops every older
  pending configuration (`acquire_acked_configuration`, `meta-window-wayland.c:1435-1460`).
- The first run of the spike, with a 750 ms quiet period between requests, met the same thing by accident:
  `evidence/first-dbus15-750ms.log`, GTK4 `back-to-primary-top-right`: 200 ms after the request the window went back
  to the previous request's rect on the other monitor and stayed.

### 7. Notes for the L1 runner

- **Startup stalls.** 3 of 12 shell starts never ran the script: the log ends after the Screencast activation, no
  `[s4]` line, until the timeout (15 and 20 minutes) or until it was stopped (11 minutes). The automation script runs only at the layout manager's
  `startup-complete` (`js/ui/main.js`, `layoutManager.connect('startup-complete', …)`), which never came. The cause
  wasn't found. Setting `SHELL_BACKGROUND_IMAGE` like the test tool didn't stop it (the third stall had it). After
  that, `run.sh` kills a shell that prints no `[s4]` line within 180 s; no stall came in the 3 runs since.
- Every run exits 1 at the end: `scripting.js` asks for `org.gnome.Shell.PerfHelper`, which isn't installed; the
  `[s4] done` line is the success signal.
- First frames after spawn: 1.4-3.8 s for the GTK clients, 0.3 s for xterm (llvmpipe).
