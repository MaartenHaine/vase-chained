# S9: the transport, the peer check and press-to-effect through a daemon

Spike S9 of the Linux Tiler (docs/linux-tiler/wayfinder.md §5, M0b row 3). It feeds §3.5 (transport and the peer
check), §3.1 (lifecycle), the "socket hop is not where latency lives" claim (§3.7.4), and the engineering default
"Transport and lifecycle [S9]".

## Question

Can a GJS extension in GNOME Shell 50.1 talk to a Rust daemon over a unix socket the daemon bound itself, using the
map's framing (versioned JSON lines)? Specifically:

- `Gio.SocketClient` connect, async line reads, EOF, reconnect with backoff;
- `Gio.Socket.get_credentials()` and `/proc/<pid>/exe` as the peer check;
- the press-to-effect time of a prefix command (Alt+A, then `\`) through the daemon under paint load.

## Answer

**Yes, and the socket costs nothing measurable end to end.** Everything the map proposes works from GJS in 50.1.

- **Peer check.** `get_credentials()` gives the daemon's own pid and uid, and `/proc/<pid>/exe` resolves, in 60-320 µs.
  When something else called `listen()` (socket activation), the peer is that process.
- **EOF.** It arrives within 0.3-70 ms of a SIGKILL. The modal pops and Alt+A is ungrabbed in the same callback.
- **Backoff and reconnect.** Backoff runs 100, 200, 400, 800, 1600, then 2000 ms. A restarted daemon is reconnected
  within one backoff step.
- **Version mismatch.** A v2 daemon is refused and never connected.
- **Press-to-effect.** It is the same with and without the socket: idle 27.7 ms vs 26.7 ms (no socket); under paint
  load 195 vs 209 ms; under heavy load 222 vs 222 ms (medians, n=40 each, headless llvmpipe).
  - The daemon round trip itself is 0.3 ms idle. Under load it is about one frame, because the key handler runs inside
    the frame dispatch and the reply is only read after that frame's paint.
  - That frame is hidden: the window's resize completes on the client's configure/ack cadence either way.

The spike also found five things the map must change. Each is in "What it decides" below:

- a synchronous socket write freezes the compositor;
- `read_line_async` has no length cap;
- an upgraded daemon binary fails the exe check until the daemon restarts;
- an unreadable (execute-only) binary or a non-dumpable daemon fails the check;
- the first key the grab sees can be a modifier.

Nothing here blocks the architecture.

## Method

All of it is at L1. A headless GNOME Shell 50.1 (gjs 1.88.0, GLib 2.88.0) runs in `chained-tiler-test` under
`dbus-run-session` and the M0a dbusrunner, with `--network=none` and the checkout read-only. Nothing touches the host
session. The `tools/before-after.sh` snapshots bracket all the runs (05:00:48 and 05:33:27): **no watched item
changed**. The only differences were the host shell's own `application_state` and someone else's python3.14 crash
report going away.

Code (throwaway, `spikes/S9/`):

- `stub/`: the stub daemon, Rust with std only, built in `chained-tiler-build` (`spikes/S9/run.sh build`: offline,
  locked, `--network=none`, into the `chained-tiler-s9-target` volume). What it does:
  - binds `$XDG_RUNTIME_DIR/vase/gnome.sock` (directory 0700) itself, or takes fd 3 from a socket-activation emulator;
  - sends a hello, answers JSON lines one connection at a time, caps its own line reads at 1 MiB, and refuses a wrong
    `v`;
  - on EOF goes back to `accept` (the §3.1 Disconnected state);
  - answers a `key` message for `\` with a `place` effect that alternates between the right half and the left 60% of
    the work area, so every press is a real resize (a Wayland configure and ack);
  - has test controls for split writes, an 8 MB line, garbage, a draw-list pad, and exit.
- `extension/`: the client, written as the real extension would be:
  - `Gio.SocketClient.connect_async` to a `Gio.UnixSocketAddress`, with backoff from 100 ms doubling to 2 s, and no
    spawning;
  - the peer check (`get_credentials()`: uid must equal ours and `/proc/<pid>/exe` must equal the expected path);
  - hello both ways, with the version checked on every line;
  - two readers: `Gio.DataInputStream.read_line_async` ("line"), or `read_bytes_async` with its own split and a
    1 MiB cap ("chunk");
  - writes only through `write_bytes_async`, from one queue with a 1 MiB cap;
  - Alt+A through `grab_accelerator` (grabbed on hello, ungrabbed on disconnect). It does a synchronous
    `pushModal(NONE)`. The next key goes to the daemon. The effects are applied with `move_resize_frame` on the
    window, which is looked up again by id. The modal pops on reply plus key release, Esc, 3 s, a 200 ms missed reply,
    or EOF;
  - the teardown is step by step;
  - it timestamps every step of a press. A `localMode` computes the same effect in the key handler with no socket,
    as the baseline.
- `l1/s9.js`: the automation script. It runs every case below, and prints `[s9] RESULT <name> <json>` lines.
  - The daemon is started from the script with `Gio.Subprocess`.
  - Keys come from a Clutter virtual keyboard, by evdev keycode.
  - Paint load is two `gtk4-demo --run=fishbowl` clients (separate processes, `--extra-filter org.gtk.Demo4`) plus
    300 half-transparent St actors moved on every frame by a `Clutter.Timeline` over the whole stage. "Heavy" adds
    8 ms of busy JavaScript per frame.
- `l1/activate.py`: socket activation done the way systemd does it. It binds and listens, forks, and the child execs
  the daemon with the socket as fd 3 (`LISTEN_FDS=1`). The parent stays.

The host was shared and loaded (1-minute load 20-41 on 12 CPUs, other spikes' containers running), and everything ran
at `nice -n 19`. Headless llvmpipe at 1280x720 painted at 13-16 fps under the load; an idle stage repaints only on
damage (about 4 fps from the test's own timers). **The absolute numbers are a slow software compositor's, not the
desktop's.** The comparisons are the evidence: with vs without the socket, the same run, the same load.

Evidence files: `spikes/S9/results/run4.log` and `run4.results` (the main run, with the no-socket baselines),
`run3.log` and `run3.results` (an earlier full run without the baselines, the same code otherwise), and `try3.log` (the
perf-helper failure under "What it decides").

## Evidence

### Peer check (`peer.ok`, `activation.peer`, `upgrade.exe`, `unreadable.exe`)

| Case | `get_credentials()` | `/proc/<pid>/exe` | Check result |
|---|---|---|---|
| daemon bound and listened itself | pid 521 = the daemon's pid, uid 1000 = ours | `/opt/s9/release/s9-stub` | ok, 57-192 µs |
| socket activation (`activate.py`) | pid 642 = **the emulator** (the process that called `listen()`) | `/usr/bin/python3.14` | refused |
| binary replaced while running (a new file renamed over the path, as `install(1)` and package tools do) | the daemon | `/run/user/1000/s9bin/vase-gnome (deleted)` | refused |
| binary mode 0111 (execute-only: the kernel marks the process non-dumpable) | the daemon | `Failed to read the symbolic link "/proc/648/exe": Permission denied` | refused |

- GJS 1.88 exposes only `Gio.Credentials.get_unix_pid()` and `get_unix_user()` (probed in the test image).
  `SO_PEERPIDFD` is not exposed, so the pid can in principle be reused between connect and the readlink. The window is
  microseconds, and §3.5 already calls the check defence in depth.
- F13 is now confirmed by experiment, not only by the man page: under activation, the peer is the listener.
- The host shell's AppArmor label is `unconfined` (`/proc/5222/attr/current`, read-only), and
  `fs.suid_dumpable=2`. INFERENCE: an unconfined reader is not stopped by the daemon's future AppArmor profile when
  it reads `/proc/<pid>/exe` (the profile's `readby` side is checked only for a confined tracer), but a
  `PR_SET_DUMPABLE(0)` in the daemon would deny it as the 0111 case did. S10 should confirm this with the real profile.

### Connect, backoff, EOF, reconnect

- **Backoff with no daemon** (`backoff.before-first-daemon`): `Could not connect: No such file or directory`.
  - Gaps 213-721 ms for the first two attempts (they overlap shell startup), then 400, 801, 1601 ms, then 2000 ms
    steady.
  - A failed connect costs 0.3-200 µs of main loop.
  - The first daemon start to hello took 1989 ms: the extension was in its 2 s step.
- **SIGKILL with the prefix armed** (`eof.sigkill`): EOF after 0.28 ms (run4) and 70 ms (run3, under paint load). The
  modal was popped 0.25 ms later in the same callback (`pop_reason: disconnect (eof)`), with `modalCount 0` and Alt+A
  ungrabbed. M1c's "kill -9 while armed releases within 250 ms" has room to spare.
- **Down** (`eof.backoff`): the killed daemon leaves its socket file, so connects now fail with
  `Connection refused`, not ENOENT. Attempts at 103, 329, 747, 1554 and 3183 ms after the kill. The restarted daemon
  removes the stale file and rebinds; hello came 638-695 ms after its start.
- **Stopped daemon (SIGSTOP)** (`hang.missed-reply`): Alt+A then `\` popped the modal 228-250 ms after the key on the
  200 ms missed-reply timer.
- **Version mismatch** (`version.mismatch`): a `--proto 2` daemon is refused on its hello (`daemon speaks v2,
  extension v1`). 4 refusals in 2.5 s on the normal backoff, no hello, Alt+A never grabbed.
- **Disable/enable** (`cycle.*`): the M0a leak checker found nothing after `disable()` (no actor, signal, source,
  grab or held object; `modalCount 0`). The daemon logged EOF. After `enable()` the hello came in 9-11 ms.

### Framing (`framing.*`)

- **A reply written in two halves 50 ms apart** arrived once, whole (round trip 112-120 ms). `DataInputStream` joins
  partial reads.
- **`JSON.parse` in the shell:** 12-19 µs for 2 KB, 62-64 µs for 64 KB, 0.73-1.03 ms for 1 MB. A 16 KB draw list in
  every reply changed nothing measurable (parse 0.03 ms; `press.paint-draw16k`).
- **An 8 MB line through `read_line_async`** was accepted: there is no cap. Parsing it took 25-38 ms, and the stage
  painted 0-1 frames in the 146-155 ms from the request to the parse, under paint load that otherwise ran at
  14-16 fps. **One oversized line stalls the compositor.**
- **The chunk reader** (`read_bytes_async(65536)`, its own split, a 1 MiB cap) closed the connection with
  `line over 1048576 bytes` after 72-105 ms. Its press latency equals the line reader's (`press.paint-chunk`).
- **A non-JSON line** is a protocol error. The connection was dropped and reconnected in 131-149 ms (one 100 ms
  backoff step).

### Writes to a daemon that doesn't read (`hang.sync-write`, `hang.async-flood`)

- **A synchronous `write_bytes` on the connection's output stream**, with a 1 s socket timeout, wrote 233,152 bytes
  (the unix socket's buffers; `net.core.wmem_default` is 212992) and then **blocked the compositor for 1004-1005 ms**
  before `Socket I/O timed out`. The stage painted 1-2 frames in that second.
- **Asynchronous writes through the queue:** 260 messages of 4 KB were queued in 5-24 ms, painting went on (16-19 fps),
  and the 1 MiB cap dropped the connection (`queue-full`, 1,047,540 bytes waiting).

More numbers:

- The daemon's own time per key was 10-28 µs, and the reply parse in the shell 10-43 µs.
- **Pings** (200 per condition, sent back to back):
  - idle: median 0.05 ms, p99 0.6-2.3 ms;
  - under paint: median 0.04 ms in run4 but 36.6 ms in run3, with p99 74-118 ms;
  - heavy: median 0.04-0.05 ms, p99 3.5-11 ms.

  A reply waits whenever a frame dispatch is under way when it arrives.
- Run3 (the same code without the baselines) gave press-to-effect 28.3 ms idle, 178 ms under paint and 246 ms heavy.
- Every series had at most one incomplete press. Each was the first press after switching series, and was either an
  effect equal to the window's current frame (the local and the stub alternation start out of step), or the first
  press of the run (next section). No press missed a reply.
- In the later series the focused, moved window was sometimes a gtk4-demo window (title "Icon") rather than the perf
  helper's. That is a busy GTK4 client, so if anything it is the more realistic case.

**Why the socket hop costs a frame and the effect doesn't.**

- Clutter queues input events and processes them in the frame clock's `before_frame` handler
  (`clutter/clutter/clutter-main.c:228` `_clutter_stage_queue_event`; `clutter-stage-view.c:938-946`
  `handle_frame_clock_before_frame` → `_clutter_stage_process_queued_events`). So the grab actor's key handler runs
  inside a frame dispatch, and that dispatch goes on to lay out and paint.
- The reply's read callback (a `PRIORITY_DEFAULT` source) is dispatched only after that. Hence "key to reply" ≈ one
  frame interval under load (49-61 ms at 14-16 fps), against 0.3 ms idle.
- In the no-socket baseline, `move_resize_frame` returns within the same dispatch (5 ms). The window's frame changes no
  earlier: the client has to get the configure, ack it and commit a buffer, which happens on its next frame callbacks
  either way. The "configure" column shows the same wait moving from one side to the other.
- INFERENCE for the desktop: on real hardware a paint takes a few ms rather than 60, so the frame the reply waits for
  is short. The end-to-end bound stays the client's configure/ack. An L3 or L4 run should repeat the with/without
  comparison on the owner's monitors before the number goes into any doc as a measurement.

### Things found along the way

- **The perf helper can't be its own paint load.** With two of the perf helper's `redraws: true` windows (the same
  process as the target window), the target never committed any resize. 18 presses applied `move_resize_frame` to the
  focused perf-helper window and got no `size-changed` or `position-changed` within 5 s. After that no window had
  focus at all (`try3.log`, the "incomplete press" lines; 38-40 of 40 missed per loaded series). L1 paint load has to
  come from separate client processes.
- **The first prefix key can be a modifier.** On the first Alt+A of run4, the grab actor's first key-press was
  keycode 56 (Left Alt, the chord's own modifier), not the command key. In `try3.log` the same happened on every
  press while no window had focus. The extension has to skip modifier-only presses inside the prefix. Why the
  modifier sometimes reaches the grab is for S2 and S3.
- **`Main.activateWindow(win)` threw** `window.get_workspace() is null` on the perf-helper window (`main.js:847`) in a
  debug run whose log wasn't kept. The script failure ended the shell. `win.activate(global.display.get_current_time_roundtrip())` works.
- **The first L1 attempt never ran the script.** The shell stayed idle for over nine minutes with no log line from
  the script. That version created the virtual keyboard at module top level and imported `leakcheck.js` by a
  `file://` URL. Moving the device creation into `run()` and using a relative import fixed it. The cause was not
  isolated.
  - gnome-shell imports the automation module before startup completes (`js/ui/main.js:335-340`). The script then runs
    only after `org.gnome.Shell.PerfHelper` appears on the bus (`js/ui/scripting.js:360-367`).
  - So L1 scripts create devices in `run()`.
- **The shell exits 1 at the end** of every S9 run, after `[s9] PASS`, with `Failed to exit helper: ...
  org.gnome.Shell.PerfHelper was not provided` (`scripting.js:309`). The perf helper had already gone. This is a
  harness nit, not a spike result.

## What it decides

**Engineering default "Transport and lifecycle" [S9]: confirmed, with these additions for the protocol spec (M1a) and
the extension (M1b).**

1. **The transport stays as §3.5 says:** the daemon binds its own socket, there is no socket activation, and the
   extension never spawns it. The peer check is uid plus `/proc/<pid>/exe`, as defence in depth.
2. **The extension never does synchronous I/O on the socket.** One blocked write froze the compositor for 1 s.
   - Writes go through one async queue with a byte cap (1 MiB). Hitting the cap is treated as a hung daemon:
     disconnect, release the grabs, back off.
   - Add a tripwire for synchronous stream calls on the connection (`write_bytes(`, `write_all(`, `write(`,
     `read_line(`, `read_bytes(`, `flush(` without `_async`), next to the existing `net-socket` wire.
   - M1b's allow-list will need the one `Gio.SocketClient` line and the one `Gio.UnixSocketAddress` line.
3. **Lines are capped.** Use the chunk reader (`read_bytes_async` plus its own split, 1 MiB per line) rather than
   `DataInputStream.read_line_async`, which takes an 8 MB line and stalls painting for about 150 ms. The daemon caps
   what it reads too. The protocol spec should also put a size budget on draw lists: 16 KB cost nothing measurable.
4. **Every line carries `v`. A mismatch is refused in both directions,** with the normal backoff and one log line.
   Re-trying is cheap and lets an upgraded daemon connect.
5. **Backoff from 100 ms doubling to 2 s is confirmed.**
   - A restarted daemon is picked up within one step (at most 2 s).
   - A killed daemon leaves its socket file. The daemon removes it before `bind`, so it must first hold a lock
     (`flock` on `$XDG_RUNTIME_DIR/vase/gnome.lock`) to stop a second daemon taking the path from a live one.
6. **Upgrades: replacing the binary makes the running daemon's exe `<path> (deleted)`,** which the check refuses at the
   next connect (a lock, or a toggle).
   - Chained's install step must restart the unit right after it lays down a new daemon binary.
   - The extension should log "daemon binary replaced; restart vase-gnome.service" for that case, not a generic refusal.
   - Doctor can check the same thing (`/proc/<pid>/exe` ends in ` (deleted)`).
7. **The binary must stay readable and the daemon dumpable.** Install it 0755 (not 0711), and the daemon must not call
   `PR_SET_DUMPABLE(0)`. Either makes `/proc/<pid>/exe` unreadable to the shell and fails the check. S10 should check
   that the AppArmor profile doesn't change this.
8. **The prefix-key rule:** the prefix grab skips modifier-only presses. S2 and S3 own the details.
9. **The lifecycle hooks behave as §3.1 needs.**
   - EOF reaches the extension within one main-loop dispatch and releases everything there.
   - `disable()` closes the socket, so the daemon sees EOF and freezes.
   - `enable()` reconnects in about 10 ms.
   - The 200 ms missed-reply timer covers a stopped daemon.
10. **L1 harness rules for later spikes and M1b:**
    - paint load and test clients come from separate processes (`--extra-filter`), never the perf helper's
      `redraws`;
    - create virtual devices inside `run()`;
    - activate windows with `win.activate(global.display.get_current_time_roundtrip())`.

**The latency claim (§3.7.4): confirmed, and reworded.**

- The socket hop costs 10-30 µs in the daemon and 0.3 ms idle. Under load it adds one frame before the reply is
  read, but press-to-effect is the same with and without it (27.7 vs 26.7 ms idle, 195 vs 209 ms paint, 222 vs
  222 ms heavy). That is because the client's configure/ack is the bound.
- §3.7.4 should say "costs one frame dispatch before the reply is read, which the client's configure round trip hides"
  rather than imply it is free.
- A blocking read in the key handler would save that frame, but it would bring back the synchronous-I/O hazard, so it
  is not recommended.
- The desktop numbers are for L3/L4.

**Round 2:** no owner question changes. The latency data supports keeping the prefix decision inside the shell (owner
answer Q1.1): arming took 0.5 ms idle and stays local.

## Blockers for the architecture

None. Two items go to other spikes:

- S10 must confirm that the daemon's AppArmor profile doesn't stop the shell reading `/proc/<pid>/exe`.
- The press-to-effect comparison should be repeated on real hardware (L3 or L4), because L1 here is a slow software
  compositor on a loaded host.
