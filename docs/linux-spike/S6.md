# S6: `Meta.Window::configure` and where a new window's first frame lands

Spike S6 of the Linux Tiler (docs/linux-tiler/wayfinder.md §5, M0b row 6, level L1). It feeds the "New windows"
engineering default (§4) and closes the open question in `gnome-api.md` §4.3.

## Question

On GNOME Shell 50.1 (mutter 50.1), for a Wayland window and an Xwayland window:

1. In what order do `global.display` `window-created` and `Meta.Window::configure` fire?
2. Does a rect set on the `MetaWindowConfig` in a `configure` handler land the window's **first frame**, with no
   move after it is shown?

## Answer

**Yes, on both, with three exceptions to design around.** `window-created` always comes first, and `configure`
follows: synchronously in the same call on Xwayland, at the client's first commit on Wayland (about 1 ms later in
every run). A handler connected inside the `window-created` handler sees it; one connected a main-loop turn later
missed it in every case. Setting position and size there put the first frame exactly on the target rect for GTK4 over
Wayland and GTK4 over Xwayland (client-side decorations), and on the target position for xlogo over Xwayland
(mutter's server-side frame; see the size exception below), with no `position-changed` or `size-changed` after the
first frame.

The exceptions:

- **Only `set_position()` and `set_size()` are usable from GJS.** `get_rect()` returns `MtkRectangle` by value, which
  GJS 1.88 reads as a pointer: it gives `null` while the rect is at (0,0) and **segfaults** once a position is set
  (inside gnome-shell, that ends the session). `set_rect()` passes the struct's address where mutter expects the
  struct, so mutter receives garbage. `get_position()`/`get_size()` lack `(out)` annotations and can't be called.
- **A Wayland window that asks to be maximized (or fullscreen) before its first commit gets no `configure` signal at
  all** in 50.x, because the maximize request sends the first configure itself. Fixed upstream in mutter 51.0 only.
- **On Xwayland, `set_size()` alone is ignored, and with a server-side frame the size is the client size**: the frame
  comes out one title bar (39 px here) taller than asked.

## What it decides

Engineering default "New windows" (§4), confirmed and sharpened:

- **The extension places new windows in `configure`, connected synchronously inside its `window-created` handler**,
  for Wayland and Xwayland alike. Xwayland needs no special path for position: its first frame lands too.
- **It calls `set_position(x, y)` and `set_size(w, h)`, always both, only when `get_is_initial()` is true.** It never
  calls `get_rect`, `set_rect`, `get_position` or `get_size` on a `Meta.WindowConfig`. `tools/linux/tripwires.txt` should get a
  wire for `.get_rect(` and `.set_rect(` (it doesn't match `get_frame_rect`) with the first extension code that
  touches `configure` (M1b), with no allow entry, because a `get_rect()` after a `set_position()` crashes the
  compositor.
- **The handler can't ask the daemon.** It runs inside a mutter signal emission, before the first configure goes out,
  so there is no round trip. The daemon keeps a **placement hint** in the extension, current at all times: where the
  next new window goes (the focused pane, or a pending launch's pane, keyed by app id for `[[app_focus]]`). The
  extension applies it in `configure` and reports the window. The daemon may move it afterwards like any other
  window. This is a protocol message for M1a (daemon to extension: `placement_hint`), not a core seam.
- **Identity for the hint lookup comes from `configure`, not `window-created`**: on Wayland, `window-created` fires
  at `get_toplevel`, before the client sets its title and app id (both null in every run), and `configure` fires at
  the first commit, when they are set. On Xwayland both are known at `window-created`. `manageable()` (`gnome-api.md`
  §4.1) is evaluated in `configure` for the same reason. (Correction to `gnome-api.md` §4.1, which says
  `window-created` fires "at the first xdg-toplevel commit": it fires at `get_toplevel`; the first commit is
  `configure`.)
- **The fallback move after the first frame stays**, but for a narrower set. The extension remembers which windows
  got an initial `configure` and moves the rest once on the actor's `first-frame`:
  - Wayland windows that request maximized or fullscreen before their first commit (no `configure`, measured;
    Firefox and other apps that restore a maximized state do this);
  - Xwayland windows whose initial state is maximized or fullscreen (`apply_config` takes those branches before the
    position one, `window.c:8586-8606`; source only, not measured);
  - windows that existed before `enable()` (no `configure` is ever emitted for them; they are adopted as today).
- **Xwayland windows with a server-side frame get `set_size(w, h - titlebar)`.** The title bar height is learned
  from the first such window (`get_frame_rect()` minus `frame_rect_to_client_rect()`), and the first-frame check
  corrects a wrong guess with one resize. Client-side-decorated Xwayland windows (GTK) land exactly.
- **The settle check after `size-changed` (F6) still applies.** The rect is constrained as a non-user operation: a
  client's minimum size wins (the perf helper stayed 640x480 when asked for 600x400), and a rect outside the work area
  is pushed fully inside it (asked at y=12 and x+w past the right edge, it landed at (680,32)). vase's panes are inside
  the work area, so the second case only matters if the work area changes between the hint and the window.
- **Nothing here blocks the architecture.** No round 2 owner question changes. Not covered here, and left to S4 and
  M1b: Electron, Ghostty and libadwaita clients, two monitors and scale 1.5, dialogs (transient windows), and windows
  restored by xdg-session-management.

- `spikes/S6/gjs-probe.sh` calls each `Meta.WindowConfig` method from plain gjs (no shell) in a separate process per
  case, three rounds, inside the same image.
- `spikes/S6/report.py` turns the event log into the table below. The event log of the second full run is
  `spikes/S6/run-2.events.jsonl`.
- Sources: mutter 50.1 (tag `8e9bb806`), gnome-shell 50.1 (tag `e0fdc4c1`), and Ubuntu's `applied/50.1-0ubuntu2.5`

## Evidence

### The source: where each signal comes from (mutter 50.1)

**Wayland.**
- `window-created`: the client's `xdg_surface.get_toplevel` request (`meta-wayland-xdg-shell.c:2257`) calls
  `meta_wayland_xdg_surface_reset()` (`:2294`), which for a toplevel makes the `MetaWindow` and calls
  `meta_wayland_shell_surface_set_window()` (`:1130-1131`), which emits `window-created`
  (`meta-wayland-shell-surface.c:165`). The surface has no buffer and usually no title or app id yet.
- `configure`: at the surface's next commit, `meta_wayland_xdg_toplevel_apply_state()` checks
  `!xdg_surface_priv->configure_sent`, builds `meta_window_config_initial_new()`, emits `configure`, then calls
  `meta_window_apply_config(..., META_WINDOW_APPLY_FLAG_ALWAYS_MOVE_RESIZE)`, which sends the first configure to the
  client (`meta-wayland-xdg-shell.c:984-994`). So the client draws its first buffer at the size the handler chose.
- A commit with a null buffer after the first one resets the toplevel (`:972-978`): a new `MetaWindow`, a new
  `window-created`, and a new initial `configure` at the next commit.
- **Why a maximized-at-start window gets none:** `xdg_toplevel.set_maximized` calls `meta_window_maximize()` straight
  away (`:462-473`); the move-resize sends a configure through `meta_wayland_xdg_toplevel_configure()`
  (`:1135-1157`, no check for the first commit), and `meta_wayland_xdg_surface_send_configure()` sets
  `configure_sent = TRUE` (`:1838`). At the first commit the check at `:984` is false, so `configure` is never emitted.
  `xdg_toplevel.set_fullscreen` takes the same route (`:490-519`). Upstream changed this in "window: Allow overriding
  client initial config" (`6f0775b7`, in tags 51.rc, 51.0 and 51.1 only): "For Wayland windows, configurations are
  postponed until the xdg_toplevel is fully configured".

**Xwayland.** On a `MapRequest` for a new window, `x11/events.c:1474-1476` calls `meta_window_x11_new()`, which ends
with `meta_display_notify_window_created()` (`window-x11.c:4003`), then calls `meta_window_x11_configure()`
(`window-x11.c:4688-4714`): it copies the window's current config (`meta_window_config_new_from`), marks it initial if
`showing_for_first_time`, emits `configure`, copies a set position and size into the size hints, and applies it with
`META_WINDOW_APPLY_FLAG_NONE`. Both signals come from one function call, before the window is mapped. Override-redirect
windows get the same pair from `MapNotify` (`events.c:1418`).

**Applying the config** (`window.c:8582-8629`). Fullscreen, then tile mode, then maximized flags are checked first;
only if none is set does a config with a position (`meta_window_config_has_position`) do
`meta_window_move_resize(MOVE | RESIZE | CONSTRAIN)` and set `window->placed = TRUE`, which turns off mutter's own
placement (`constraints.c:566-571`). Without a position, a Wayland config still resizes (`ALWAYS_MOVE_RESIZE`), and an
X11 one does nothing. `set_position()` sets `has_position` (`meta-window-config.c:194-203`); `set_size()` doesn't
(`:219-227`). The rect is a frame rect (`window.c:4181-4198`); without `USER_ACTION` the constraints keep it fully
on-screen inside the work area and on one monitor.

**gnome-shell 50.1 itself** never connects `configure` (`js/` and `src/` grep). Mutter's own test
`src/tests/window-config-tests.c` does exactly what the Tiler would (connect `configure` in `window-created`,
`set_position(50,75)` + `set_size(300,200)` on the initial config) and asserts the result for Wayland and X11 clients.

The typelib (read with GIRepository in the same image): `meta_window_config_get_rect () -> interface` and
`meta_window_config_set_rect (rect:interface)`, both **not** pointers, and `get_position (x:gint32*, y:gint32*)` with
direction `in` (the header, `meta-window-config.h:41-60`, has no annotations). INFERENCE: GJS treats the by-value
struct as a pointer: a zero rect reads as a null pointer, `x,y` = (120,102) reads as an invalid address, and after
`set_rect()` the "rect" is the address of the JS-side `Mtk.Rectangle`, which GJS then frees twice.

- `rect` mode: mutter logged `Constraining W1 (gnome-shell-perf-helper) in move from 0,0 0x0 to 1103565104,23877
  1763397024x32766` (a heap address split into x and y); the constraints clamped it to the whole work area,
  (0,32) 1280x688, and the window appeared there.
- `position` mode with a `get_rect()` after `set_position()`: gnome-shell died inside the handler; the client logged

Read with the per-event lines:

- **Order:** `window-created` came first in all 36 cases. `configure` followed after 0.7-2.0 ms on Wayland and
  0.4-3.1 ms on Xwayland (the Xwayland gap is the logging between two synchronous emissions). Every `configure`
  had `get_is_initial()` true and came once per window. `shown` was logged for every Wayland window and only for
  some Xwayland ones; the actor's `first-frame` came in every case.
- **The first frame lands:** in every `possize` case the `position-changed`/`size-changed` before `first-frame` were
  logged with `hidden: true` and the actor not yet visible, and the frame at `first-frame` was the final one. The
  frame at `shown` already had the target position. Nothing moved afterwards.
- **Wayland identity:** at `window-created`, `title`, `gtkAppId` and `wmClass` were null for perf-wl, perf-wl-max
  and gtk4demo-wl, and the frame was 0x0; at `configure` they were `gnome-shell-perf-helper` /
  `org.gnome.Shell.PerfHelper` and `GTK Demo` / `org.gtk.Demo4`. `get_pid()` was known at both. On Xwayland the title,
  `WM_CLASS` (`gtk4-demo`, `XLogo`) and the GTK app id were known at `window-created`, and the frame was the client's
  own request (`[0,0,300,200]`, `[40,300,300,200]`, `[14,32,800,600]`).
- **Min size wins:** the perf helper sets a min size of 640x480 after its first commit (`Window W0 sets min size 640 x
  480`); asked for 600x400, it settled at 640x480 at the asked position.
- **`size` alone:** on Wayland the size was used and mutter centred the window (gtk4-demo at (340,176) 600x400); on
  Xwayland it was ignored (no position, so `apply_config` does nothing).
- **X11 frame:** xlogo asked for 600x400 came out 600x439: mutter's frame (drawn by `mutter-x11-frames`) adds a 39 px
  title bar around the client size. The control xlogo, 300x200, likewise came out 300x239. gtk4-demo over X11 (CSD,
  `_GTK_FRAME_EXTENTS`) came out exactly 600x400.
- **Late connect:** the handler connected from the idle never ran (no `configure` was logged after
  `late-connect`), and the window got mutter's default placement, the same frame as in `control`. On Xwayland that
  is certain (the two signals are one call); on Wayland the first commit came within about 1 ms, before the idle.
- **Maximized at start:** perf-wl-max logged `notify::maximized-horizontally` 0.4 ms after `window-created`, mutter
  logged `Constraining W6 (gnome-shell-perf-helper) in move from 0,0 0x0 to 0,32 1280x688` before any commit, and no
  `configure` came in any of the six modes.

Timing from `window-created` to `first-frame`: 43-335 ms on Wayland and 6-148 ms on Xwayland, under llvmpipe on a
host with a load average of 40-44 (the first window of a run took 1.6 s). This is client start-up, not configure.

frames in all 18 cases.
