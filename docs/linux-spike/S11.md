# S11: does the devkit run under the L3 recipe?

Spike S11 of the Linux Tiler (docs/linux-tiler/wayfinder.md §5, M0a "S11 first"). It feeds round 2 and the
engineering defaults.

## Question

Does `gnome-shell --devkit` run under the L3 recipe (`tools/dev-shell.sh`): private, empty system and session buses,
a private `XDG_RUNTIME_DIR`, `GSETTINGS_BACKEND=keyfile`, the `tiler-dev` mode with only the hello extension, and
the viewer on the host compositor, with no change to the real desktop? If not, L3 is dropped and the plan runs on L1
plus the owner's L4 assessment.

## Method

`sh tools/dev-shell.sh` from a terminal on the desktop (GNOME Shell 50.1 Wayland), between two read-only
`tools/before-after.sh` snapshots of the real session, compared afterwards. The connections of the nested shell and
the viewer were read from `/proc` and `ss -xp` while it ran, without touching any bus. Three runs: the first stopped
at the recipe's own mode check, the recipe was fixed, the second ran to the end. A third run, after the M0a branches
were merged, checks the same recipe with the merged hello extension (`vase-hello@maartenhaine.github.io`).

## Answer

**Yes (second run, below). L3 is kept.** The devkit shell ran on the private, empty system and session buses
and a private `XDG_RUNTIME_DIR`, in the `tiler-dev` mode with the hello extension enabled, and the viewer reached the
host compositor through the absolute `WAYLAND_DISPLAY`. The before-after check found no change at all on the host.

## What it decides

- **Round 2 / the map:** L3 stays as a test level. The fallback to L1 plus the owner's L4 assessment isn't needed.
  Extension toggles, locks and unlocks stay at L1 only.
- **Engineering defaults:** an L3 run goes only through `tools/dev-shell.sh` (one at a time), between before-after
  snapshots. The mode is proven twice (gnome-shell's own loader in plain gjs before the start, the private bus after
  it), never with `gnome-shell --list-modes`, which segfaults in 50.1. Every run is under `RLIMIT_CORE` 1 so a crash
  leaves no apport report. The extension lists `session-modes` `["user", "tiler-dev"]` and never `unlock-dialog`; the
  metadata lint enforces both.
- **Open for later spikes:** the nested shell's `_xkbOptions` error at startup (check the nested keymap before
  trusting an S2 key result at L3), and whether the label shows in the viewer (the owner's first look).

## Evidence

The first run, recorded next, stopped at the recipe's own mode check before gnome-shell ran. The first two runs used
the S11 branch's own hello extension, `vase-hello@vase-chained`, and v2 before-after snapshots; the merged tree has
the skeleton's `vase-hello@maartenhaine.github.io` and v3 snapshots (the tree hash leaves out the host shell's own
churn files).

### First run: stopped at the mode check

The recipe refused to start, at its own check, before gnome-shell ran. The devkit never started and no viewer window
opened.

**Host:** Ubuntu, GNOME Shell 50.1-0ubuntu1.5 Wayland session, libmutter-18-0 and mutter-dev-bin 50.1-0ubuntu2.5.
The host was under heavy load (load average about 64).

**What happened** (`tools/dev-shell.sh`, no arguments; run dir `~/.cache/tiler-dev.TfqNNeFl`):

1. Stage A (host checks, run dir, mode file, keyfile) and stage B (the private system bus) passed.
2. In stage C, the check that the `tiler-dev` mode loads runs `/usr/bin/gnome-shell --list-modes`. That process
   crashed with SIGSEGV, so its output didn't contain `tiler-dev`, and the recipe stopped:
   `refusing to start: gnome-shell --list-modes doesn't list tiler-dev; it would fall back to the 'user' mode`.
3. The cleanup trap ran. No process with the run's `TILER_DEV_RUN` marker was left, and no `mutter-devkit` ran.

**Why `--list-modes` crashes.** From the core, with gdb offline and no debug symbols: the crash is in
`gjs_context_eval_module()` ← `gjs_context_eval_module_file()` ← gnome-shell's `--list-modes` option callback ←
`g_option_context_parse()` ← `meta_context_configure()` ← `main()`. In 50.1 the option runs while the command line
is parsed, before the shell has a display or a bus. INFERENCE: this is a gnome-shell 50.1 bug in `--list-modes`, and
it would crash with any environment, not just the recipe's. To check that would mean crashing it again, which writes
another crash report (see below), so it wasn't run again.

**Before-after** (`tools/before-after.sh`, 03:32:45 and 03:34:04): **no watched item changed**, and nothing in the
unwatched list changed either. dconf hash, LockedHint (`no`), crash marker (absent), the `~/.local/share/gnome-shell`
tree hash, the `monitors.xml` mtime and hash, the owners of `org.gnome.Shell` (pid 5222), polkit, NetworkManager and
login1, the host shell's bus connections, `shell_pids` and `leftovers=0` all match.

**One change on the host that the check doesn't watch.** Apport (`kernel.core_pattern` pipes to it) wrote
`/var/crash/_usr_bin_gnome-shell.1000.crash` (8.9 MB, 03:33, `ProcCmdline: /usr/bin/gnome-shell --list-modes`).
whoopsie is inactive, so it wasn't uploaded. On the next login, Ubuntu may show it as a "system program problem".
It was left in place so the owner can decide; it can be deleted by hand. Any process the recipe starts that crashes
leaves a report like this, so `before-after.sh` should list new files in `/var/crash`.

**Small fault found along the way.** In both scripts' `/proc/*/environ` scans, `tr ... <"$e" 2>/dev/null` opens the
file before stderr is redirected, so dash prints `cannot open /proc/N/environ: Permission denied` for every process
of another user. The result is still correct, but the output is full of noise. The fix is `2>/dev/null <"$e"`, or a
`{ ...; } 2>/dev/null` around the loop.

**Decision the map asks for (keep L3, or drop it for L1 plus L4): not taken after the first run** (taken after the
second, below). The finding says nothing about the devkit itself, only about one of the recipe's checks. M0a stays at "S11 first", and nothing is built on L3 until S11
runs to the end. Options for the owner:

- **(a) Keep L3 and replace the check.** Prove that the mode loaded without `--list-modes`, for example by loading
  `sessionMode.js`'s mode file the same way the shell does, outside gnome-shell, or by stopping the run as soon as the
  shell log shows it fell back to `user` (sessionMode.js:149-152). The isolation checks don't change. This changes a
  safety check that two reviews passed, so the change needs its own review, then S11 runs again.
- **(b) Drop L3 now** and use L1 plus the owner's L4 assessment, as the map's fallback says.

Recommendation: (a). The failure is a bug in one check, not evidence against the devkit.

### S11 fix: the mode check without `--list-modes` (2026-11-07)

Option (a) above, taken so S11 can run again. It passed two reviews before the second run. gnome-shell wasn't started
while it was written.

**What the shell does with a mode** (gnome-shell 50.1 `ui/sessionMode.js` and `misc/fileUtils.js`, read from the
installed `libshell-18.so`): `_loadModes()` walks `gnome-shell/modes` in each `XDG_DATA_DIRS` entry in order (not
`XDG_DATA_HOME`), names a mode after its file name up to the first `.json`, keeps the first file of each name that
`JSON.parse` accepts, skips a failed one without a word, and marks every loaded mode primary. SessionMode's
constructor then uses `--mode` if that mode is loaded and primary, and `'user'` otherwise.

**Before the start, the shell's own loader** (`tools/mode-check.js`, run with plain gjs in stage C's environment):
the two files are extracted from `libshell-18.so` at run time and must match pinned sha256s (another build is
refused until they are read again); four stubs stand in for imports the loader never reads. The check proves the
mode file is the only file in any modes dir that can define `tiler-dev`, that it sits in the first data dir, that it
parses the way `_loadMode` parses it (same libgjs and libmozjs-140 as gnome-shell) with no `parentMode`, no
components and only the extension; then it runs the real `listModes()`, which prints exactly the modes the
constructor accepts, and the recipe requires `tiler-dev` among them. Tried in a scratch tree: a good file passes;
broken JSON, a `parentMode`, a second `tiler-dev.json.bak` and a wrong first data dir are each refused, and the real
loader alone drops the broken file from its list.

**After the start, signs on the private session bus**, polled every 0.2 s; the shell is killed (SIGKILL) at the
first wrong sign, or if there is no proof 90 s after the start:
- `org.gnome.keyring.SystemPrompter` has no owner. Only `user` has components, and the keyring component claims
  that name, so a fallback shows as soon as the components start, before `org.gnome.Shell` is exported.
- `org.gnome.Shell`'s `Mode` is `tiler-dev`. **This alone proves nothing about the fallback:** `Mode` returns
  `global.session_mode`, the `--mode` argument (`shellDBus.js`, `get Mode`), not the mode SessionMode settled on.
  It only proves the option arrived.
- `GetExtensionInfo(uuid)` says `enabled: true`. That field is whether the uuid is on the extension manager's enabled
  list, which with the keyfile's `disable-user-extensions=true` is the running mode's `enabledExtensions` and nothing
  else; `user` has none. It doesn't depend on the extension's own code working. This is the positive proof.

Tried against a fake shell on a private bus: the right signs pass; `Mode` `user`, `enabled: false` and an owned
keyring prompter are each refused.

**How bad a few seconds in `user` would be.** It can only happen before the kill, since the components start
inside `_initializeUI()`, before `org.gnome.Shell` exists. On these buses:
- the polkit agent and the NetworkManager secret agent register with services that aren't on the private system
  bus, and nothing can activate them, so no authentication or Wi-Fi secret is ever asked for;
- the keyring prompter claims its name on the private session bus, where the real gnome-keyring-daemon never looks;
- no ScreenShield, as in `tiler-dev`: `canLock()` asks GDM on the private system bus and gets no answer;
- the automount manager mounts, once at startup, every volume the volume monitor offers. With
  `GIO_USE_VOLUME_MONITOR=unix` and no gvfs or udisks on the buses that is fstab entries marked `user`, and this
  host's fstab has none (its NFS entries are `noauto,x-systemd.automount`);
- the rest is UI inside the viewer: the fuller panel and quick settings (whose NetworkManager, Bluetooth and power
  items find nothing on the buses, and whose sound item finds no PulseAudio socket in the private runtime dir),
  and maybe the welcome dialog; no extension runs.
Files, the host Wayland socket and PipeWire are the same in both modes. So a short fallback is a nested shell with a
fuller UI and three agents talking to nobody. The checks keep it short, and the owner's "never in a `user`-parent
mode" rule still holds for any run that gets past them.

**Crash reports.** Apport writes a report whatever the core ulimit: the `--list-modes` crash came in at `core limit
0` (`/var/log/apport.log`). A limit of exactly 1 byte is the kernel's own "skip the `core_pattern` pipe" value. Tried
with an unpackaged copy of `sleep`: at 0, apport was called and ignored it; at 1, the kernel logged
`RLIMIT_CORE is set to 1, aborting core`, apport wasn't called, and `/var/crash` didn't change. The recipe now runs
stages B and C under `prlimit --core=1` (soft and hard, so nothing inside can raise it), and stage C refuses if the
limit isn't 1. A crash still prints its backtrace to `shell.log` (`SHELL_DEBUG=backtrace-segfaults`), but leaves no
core.

**before-after.sh** now records every entry of `/var/crash` and `~/.local/share/apport` (type, size, mtime, path:
names only, since other users' reports aren't readable). A report that appears or changes fails the check; one that
goes away is listed but doesn't. Snapshots are v2, and a v1 snapshot is refused. Both scripts' `/proc/*/environ`
scans now redirect stderr before opening the file, so permission errors are silent.

### Second run: the devkit runs (2026-11-07, 03:59-04:01)

**Setup:** the same host and packages as the first run (load average about 46). `sh tools/dev-shell.sh` with no
arguments (`just` isn't installed), started from the agent's shell with the desktop's `WAYLAND_DISPLAY=wayland-0`,
`XDG_RUNTIME_DIR=/run/user/1000` and session bus; run dir `~/.cache/tiler-dev.PaTCIzQe` (6.1 MB, kept with its logs).

**What happened:**

1. Stages A to C passed, the mode check included, and gnome-shell started as
   `gnome-shell --wayland --devkit --mode=tiler-dev --no-x11` (03:59:17.5).
2. The extension logged `vase-hello@vase-chained: enable` at 03:59:20.65, and the bus check passed right after:
   `Mode 'tiler-dev', vase-hello@vase-chained enabled, no keyring prompter`. The shell logged `GNOME Shell started` at
   03:59:24. It ran for about two minutes, with nothing new in its log after startup.
3. It was stopped the way Ctrl+C stops it: SIGTERM to the stage C shell, which passes it on to gnome-shell
   (`Shutting down GNOME Shell`, `Removed virtual monitor Meta-0`, 04:01:21). The run exited 0, the cleanup trap ran,
   no process with a `TILER_DEV_RUN` marker was left, and only the host shell (pid 5222) and no `mutter-devkit` ran
   afterwards.

**Where the devkit's connections went** (read from `/proc` and `ss -xp` while it ran, without touching any bus):

- The viewer, `/usr/libexec/mutter-devkit`, had `WAYLAND_DISPLAY=/run/user/1000/wayland-0`, and that socket's peer
  was the host shell (pid 5222). Its other sockets went to the run's two dbus-daemons, to the nested shell, and to
  the host's `/run/user/1000/pipewire-0`, where the host's PipeWire linked `gnome-shell:output_1` to
  `mutter-devkit:input_1`. So the absolute `WAYLAND_DISPLAY` works, and so does `PIPEWIRE_REMOTE`.
- The nested shell listened on `<run dir>/run/wayland-0`. Its crash marker `gnome-shell-disable-extensions` was in
  the private runtime dir, and ibus-daemon's socket was in the run dir's cache.
- Neither the nested shell nor the viewer held a connection on the host session or system bus (`busctl --user` and
  `--system list`), and `org.gnome.Mutter.Devkit` had no owner on the host session bus.

**The shell's log** (`log/shell.log`, 94 lines). Every warning and error, and why:

- `Unknown experimental feature 'scale-monitor-framebuffer'` and `'xwayland-native-scaling'`: INFERENCE: the
  default of `org.gnome.mutter experimental-features` in Ubuntu's schema still lists features that mutter 50 no
  longer has; the keyfile doesn't set the key.
- `There is no colord server available`; `Error registering session with GDM` and `Error registering display with
  GDM` (`org.gnome.DisplayManager` unknown); `Failed to inhibit suspend` (`org.freedesktop.login1` unknown): the
  private buses have none of these services, as intended.
- timeLimitsManager: `Could not get a proxy for user 1000` (login1 unknown), then `Failed to start state machine`
  (`this._loginUser is null`), and accountsservice: `user (null) has no username`. The same cause: no logind and no
  AccountsService.
- `portal is not running: ... org.freedesktop.portal.IBus`: no portal on the private session bus.
- `CRITICAL: TypeError: can't access property "join", this._xkbOptions is undefined`, in
  `keyboardManager.js:208` (`_buildOptionsString`), reached from `ibusManager` `_onConnected` →
  `keyboard.js` `_ibusReadyCallback` → `activateInputSource`. INFERENCE: IBus became ready before the input source
  manager had read the xkb options, so the first keymap apply threw. The shell carried on. This is the only error
  that may matter later: S2 tests keys at L3, so check whether the nested keymap is right before trusting a key
  result there.
- No error came from the extension. Its label wasn't checked on screen (no one was at the desktop). The log has
  `enable` and no `disable`: INFERENCE: the shell doesn't disable extensions when it shuts down on SIGTERM.

**Before-after** (`tools/before-after.sh`, v2 snapshots at 03:58:59 and 04:02:08): **no watched item changed, and
nothing else changed either**; the compare listed no difference at all. dconf hash, LockedHint (`no`), crash marker
(absent), the `~/.local/share/gnome-shell` tree hash, the `monitors.xml` mtime and hash, the owners of
`org.gnome.Shell` (pid 5222), `org.gnome.Mutter.Devkit` (none), polkit, NetworkManager and login1, the host shell's
bus connections, `shell_pids` (5222), `leftovers=0` and the crash report list match. `/var/crash` gained nothing:
the first run's `_usr_bin_gnome-shell.1000.crash` is still there for the owner.

**The disable/enable cycle wasn't tried.** The recipe offers no way to do it, and the map puts extension toggles at
L1 only ("Locks, unlocks and extension toggles are tested here, and nowhere nearer the real session", §5). It stays
for the L1 hello run in `chained-tiler-test`.

**Decision: keep L3.** S11's question is answered yes: the devkit runs with private, empty system and session buses
and a private `XDG_RUNTIME_DIR`, in the `tiler-dev` mode, and the viewer reaches the host compositor through an
absolute `WAYLAND_DISPLAY`, with no change on the real desktop. The fallback to L1 plus the owner's L4 assessment is
not needed. M0a's "the hello extension runs at L3" is met, but only on the log and bus evidence; whether the label
shows in the viewer is for the owner's first look. Still open for later spikes: the `_xkbOptions` error above, and
the `Lock` signal question (only relevant if the private bus were dropped, which it isn't).

### Third run: the merged tree (2026-11-07, 04:46-04:48)

**Why:** the M0a branches were merged into `linux-tiler` (hardening, skeleton, S11). The hello extension is now the
skeleton's `vase-hello@maartenhaine.github.io` with `session-modes` `["user", "tiler-dev"]`, and `before-after.sh`
writes v3 snapshots.

**Setup:** the same host and packages (load average about 29). `nice -n 19 sh tools/dev-shell.sh`, no arguments, from
the agent's shell with the desktop's `WAYLAND_DISPLAY=wayland-0`, `XDG_RUNTIME_DIR=/run/user/1000` and session bus;
run dir `~/.cache/tiler-dev.0fov6Bc2`, kept with its logs.

**What happened:**

1. Stages A to C passed, the mode check included, and gnome-shell started as
   `gnome-shell --wayland --devkit --mode=tiler-dev --no-x11`.
2. The extension logged `[vase-hello] enable` at 04:47:01.25, and the bus check passed:
   `Mode 'tiler-dev', vase-hello@maartenhaine.github.io enabled, no keyring prompter`. So the merged extension is
   the one the mode enables, and the mode file and `mode-check.js` took its uuid from `metadata.json`.
3. While it ran, the run's processes were the two private dbus-daemons, gnome-shell, the viewer `mutter-devkit`, the
   ibus processes, and a glycin SVG loader in its own `bwrap` sandbox (an image loader gnome-shell starts, with
   `XDG_RUNTIME_DIR` in the run dir). On the host buses only the host shell (pid 5222) held connections, and
   `org.gnome.Mutter.Devkit` had no owner there.
4. It ran about 35 s and was stopped with SIGTERM to the stage C shell (`Shutting down GNOME Shell`, `Removed virtual
   monitor Meta-0`, 04:47:35). The run exited 0, and afterwards no process carried a `TILER_DEV_RUN` marker and only
   the host shell ran.

**The shell's log:** the same warnings as the second run, from the missing services on the private buses (login1,
GDM, colord, AccountsService, the IBus portal), and the same `this._xkbOptions is undefined` CRITICAL in

**Before-after** (v3 snapshots at 04:46:41 and 04:48:07): **no watched item changed, and nothing else changed
either**; the compare listed no difference at all, the shell's own churn files included. `/var/crash` gained nothing.
The v3 compare was also checked against two edited copies of the after snapshot: a change to `application_state`
alone is listed as not watched and passes; a changed `locked_hint` fails.

**Decision unchanged: keep L3.**
