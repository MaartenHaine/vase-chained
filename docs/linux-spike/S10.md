# S10: what a `systemd --user` sandbox really does on this desktop

Spike S10 of the Linux Tiler (docs/linux-tiler/wayfinder.md §5, M0b row 4). It checks F12 and §3.6, and feeds Q3.4
(the audit text) and Q3.8 (doctor). This finding covers the half that needs no sudo. The AppArmor half needs the
owner's sudo, and its exact steps are at the end. Its result goes into the "AppArmor half" section once it has run.

## Question

The kernel is 7.0 with Ubuntu's `kernel.apparmor_restrict_unprivileged_userns=1`. In a transient
`systemd-run --user` unit, does each namespace option the confinement plan could use make the unit fail, or does the
unit start without it? Does each seccomp option apply (`Seccomp: 2` in `/proc/<pid>/status`)? And does the §3.6
option set work as a whole?

## Answer

**The namespace options never confine. Every seccomp option applies.**

- **Namespace options: none of them confines a user unit here.** Each one does one of three things:
  - **It does nothing, and nothing is logged at the default level.** This covers `ProtectSystem=`, every
    `ProtectHome=` mode, `PrivateTmp=`, `PrivateMounts=`, `ReadOnlyPaths=`, `InaccessiblePaths=`, `ReadWritePaths=`,
    `NoExecPaths=`, `ProtectControlGroups=` and `ProtectKernelTunables=`'s read-only `/proc/sys`. The unit starts,
    `$HOME` is still listable and writable, and the mount namespace is the host's. There is a side effect: each of
    these options makes systemd create a user namespace first. The kernel then moves the process into AppArmor's
    `unprivileged_userns` profile, so `attr/current` reads `unprivileged_userns (enforce)` instead of `unconfined`.
    `ProtectProc=`, `ProcSubset=` and `RestrictFileSystems=` also do nothing, but without the user namespace.
  - **The unit starts and a line in the journal says the option was dropped:** `PrivateNetwork=` ("proceeding
    without"), `PrivateIPC=` and `ProtectHostname=` ("ignoring"), and `IPAddressDeny=` ("not running as root").
    `ProtectHostname=` also loses its seccomp filter, so `sethostname` isn't filtered.
  - **The unit fails to start:**
    - `PrivateUsers=identity` (217/USER);
    - `PrivatePIDs=` and `TemporaryFileSystem=` (226/NAMESPACE);
    - every option that shrinks the capability bounding set: `CapabilityBoundingSet=`, `PrivateDevices=`,
      `ProtectClock=`, `ProtectKernelModules=` and `ProtectKernelLogs=` (218/CAPABILITIES, "Failed to drop
      capabilities: Operation not permitted").
- **Seccomp options: every one applies**, with `NoNewPrivs: 1` implied. Each one passed its own test (§2 below).
  - `MemoryDenyWriteExecute=` is the exception to the `Seccomp: 2` check: systemd uses the kernel's
    `PR_SET_MDWE` instead of a filter, so it shows `Seccomp: 0`, and `/proc/<pid>/status` has no field for MDWE.
  - `SystemCallFilter=~execve` stops the unit from starting (203/EXEC).
  - Removing `@process` breaks threads.
- **§3.6's set works as a whole** (case p01): the unit runs with `NoNewPrivs: 1`, `Seccomp: 2`, 14 filters and MDWE
  on, and passes every one of those tests. A unix socket can still bind and listen, threads start, and
  `posix_spawn` still works. Adding `CapabilityBoundingSet=` stops it from starting (p00). Adding
  `ProtectHome=read-only` and `PrivateNetwork=yes` changes nothing except the label, which becomes
  `unprivileged_userns` (p02).

So F12 is answered: **mostly silent, sometimes fatal, never a sandbox.** Nothing in the architecture is blocked. §3.6
already claimed only the seccomp options, and the file, exec and network limits were always meant to come from the
AppArmor profile. Two things change in that plan: "minus the process-spawning groups" can't be done with seccomp, and
the unit must carry no namespace option at all (see "What it decides").

## What it decides

- **The daemon unit (§3.6, engineering default).** Exactly these options, as measured in p01:
  `NoNewPrivileges=yes`, `RestrictAddressFamilies=AF_UNIX`, `SystemCallFilter=@system-service`,
  `SystemCallFilter=~@privileged @resources`, `SystemCallArchitectures=native`, `LockPersonality=yes`,
  `MemoryDenyWriteExecute=yes`, `RestrictNamespaces=yes`, `RestrictRealtime=yes`, `RestrictSUIDSGID=yes`, plus a
  `SystemCallErrorNumber=` choice (next point).
  - **No namespace option, not even a harmless-looking one.** Each one is either a silent no-op, a logged no-op
    or a unit that won't start. The no-ops are worse than useless: they relabel the daemon `unprivileged_userns`
    before it execs. That would hide the vase profile from doctor's label check, and it may stop the profile from
    attaching at all (case a3 of the AppArmor half checks that).
  - **No `CapabilityBoundingSet=`, `PrivateDevices=`, `ProtectClock=`, `ProtectKernelModules=` or
    `ProtectKernelLogs=`**: the unit won't start.
  - Chained's unit lint should reject the whole list (each option in `exec_needs_cap_sys_admin`, below) so that
    nobody adds one later to "harden" the unit.
- **The §3.6 text "minus the network and process-spawning groups" is corrected.**
  - `execve` can't be filtered, because systemd installs the filter before it execs the daemon (s05: 203/EXEC).
  - `@process` can't be removed, because it holds `clone`/`clone3`, so threads fail (s06: `can't start new thread`).
  - `@network-io` can't be removed either, because the daemon needs `socket`/`bind`/`listen` for its unix socket.
  - So the families are limited by `RestrictAddressFamilies=AF_UNIX`, and a ban on exec has to come from the
    AppArmor profile (no `x` rules) or from the daemon itself.
- **`SystemCallErrorNumber=`**: the unit was tested both ways.
  - With `EPERM`, a call outside the filter fails quietly.
  - With the default (kill), the daemon dies with SIGSYS, `Restart=on-failure` brings it back, and the kernel
    logs an audit record naming the call (`type=1326 ... syscall=144`, which is `sched_setscheduler` in
    `@resources`).
  - Recommendation (engineering default): the default kill action at L0/L1, so a missing call shows up there,
    and `EPERM` in the shipped unit, so a call that only a rare path makes degrades instead of crash-looping.
  - Whichever is chosen, the unit needs `LimitCORE=1`. A SIGSYS death otherwise leaves an apport report in
    `/var/crash` ("Leftovers and the host", below).
- **Doctor (Q3.8).**
  - `NoNewPrivs: 1` and `Seccomp: 2` from `/proc/<pid>/status` work as planned: p01, and the live process in the
    dry run's a7.
  - MDWE can't be seen there. The daemon reports `prctl(PR_GET_MDWE)` in its hello, and doctor compares that.
  - Doctor should also FAIL if `attr/current` is `unprivileged_userns`. That label means someone added a namespace
    option.
  - The filter count (14 here) depends on the systemd version, so it isn't a doctor check.
- **The audit text (Q3.4).** The daemon condition reads: "seccomp options as above, checked live; no systemd
  namespace sandboxing (it doesn't apply to user units on Ubuntu with the user-namespace restriction); file, exec
  and network limits from the AppArmor profile". The last clause is pending the AppArmor half.
- **One more option, not a decision.** Landlock is in this kernel's LSM list, at ABI 8 (`landlock_create_ruleset`
  with `LANDLOCK_CREATE_RULESET_VERSION`). With it, the daemon could restrict its own file access, exec and abstract
  unix sockets without sudo. If the AppArmor half shows that the profile doesn't attach, Landlock is the fallback.
  Even if it does attach, Landlock is a second layer that also works on the owner's other Linux devices. It would
  need one small dependency or about 100 lines of `unsafe` syscalls, so it's a question for M1a, not a default now.

## Method

- **Where it ran.** On the desktop: Ubuntu 26.04.1, kernel 7.0.0-42-generic, systemd 259.9-0ubuntu0.1, GNOME Shell
  50.1. It ran as the owner's user from a normal terminal, with no sudo. The driver ran in the initial namespaces
  (user `4026531837`). The user manager (pid 4779) is `unconfined`, `NoNewPrivs: 0`, `Seccomp: 0`, and has only
  `CAP_WAKE_ALARM` in `CapEff`.
- **The driver, `spikes/S10/run.sh`.** It starts one transient unit per case:
  `systemd-run --user --wait --pipe --collect -p Nice=19 -p IOSchedulingClass=idle -p RuntimeMaxSec=60
  -p LimitCORE=1`, plus the case's options. The driver itself runs under `nice -n 19`, and it waits while the
  1-minute load is 40 or more (it waited twice). For each case it saves the unit's result, the probe's output and
  the user journal's lines for that unit under `spikes/S10/results/<run>/`.
- **The probe, `spikes/S10/inner.py`.** It travels in the unit's environment (`S10_CODE`), so it needs no file under
  `$HOME`, which `ProtectHome=` might hide. It reads its own `NoNewPrivs`, `Seccomp`, `Seccomp_filters`, `CapEff`,
  `CapBnd`, `attr/current`, `PR_GET_MDWE`, the seven namespace ids against the driver's and its `uid_map`. Then it
  tries, and reports the errno of, each of these:
  - list `$HOME` and write into a 0700 `~/.cache/s10-probe.*` dir;
  - read the mount options of `/proc/sys`, `/usr`, `/home`, `/tmp` and `/sys/fs/cgroup`;
  - look at `/dev`, the other pids, the network interfaces and `/dev/kmsg`;
  - make `AF_UNIX`, `AF_INET` and `AF_NETLINK` sockets, and bind and listen on a unix socket;
  - map W+X memory and `mprotect` RW to RX;
  - `personality(PER_LINUX32)`;
  - `sched_setscheduler(SCHED_FIFO, 0)`: the kernel answers EINVAL, a seccomp refusal EPERM;
  - `chmod 4755` on its own file;
  - `ptrace(PEEKDATA, self)`: ESRCH from the kernel; ptrace is in `@debug`, outside `@system-service`;
  - `sethostname`, `klogctl`;
  - `unshare` of a user, a UTS and a net namespace (in a forked child);
  - `posix_spawn("/usr/bin/true")`, and starting a thread.
  
  Where a `SystemCallFilter=` is under test, the case sets `SystemCallErrorNumber=EBADE`, so a filter refusal shows
  as the odd errno `EBADE` instead of the kernel's own EPERM.
- **The sources.** The explanations come from systemd v259 sources (`src/core/exec-invoke.c` sha256 `25c829d5…`,
  `src/shared/seccomp-util.c`), fetched to `~/.cache/s10-src/` and read there. The kernel's AppArmor audit lines
  were read with `journalctl -k` (the owner is in `adm`). No log level was raised on the user manager.
- **Runs.** `20261107T045629` ran all cases. `20261107T050224` ran the §3.6 set on its own, after the first run
  showed that `CapabilityBoundingSet=` breaks it; the first run's two old plan cases were deleted as superseded.
  `20261107T050339` ran the two SIGSYS cases again under `LimitCORE=1`. `aa-dry-*` is the AppArmor script's dry run
  (stock binaries, no profile).

**Why, from systemd v259 and the kernel log:**

1. **A user unit gets an implicit user namespace first.** In a user manager, any option in
   `exec_needs_cap_sys_admin()` (`exec-invoke.c:4509-4552`: `PrivateTmp`, `PrivateDevices`, `PrivateNetwork`,
   `PrivateIPC`, `PrivateMounts`, `ProtectSystem`, `ProtectHome`, `ProtectKernel*`, `ProtectClock`,
   `ProtectHostname`, bind mounts, temporary file systems, and more) makes the executor set up a user namespace
   before anything else. It uses `PrivateUsers=self` if none was asked for (`:5831-5858`).
   - If that fails and `PrivateUsers=` was explicit, the unit fails (`:5848-5851`, which is case n02).
   - Otherwise the failure is logged at info level and ignored (`:5852-5853`).
   
   Here the namespace itself is created: mapping only one's own uid needs no privilege.
2. **Ubuntu's restriction then takes every capability inside it.** The kernel logs `apparmor="AUDIT"
   operation="userns_create" info="Userns create - transitioning profile" profile="unconfined"
   execpath="/usr/lib/systemd/systemd-executor" target="unprivileged_userns"`. The executor is now in
   `/etc/apparmor.d/unprivileged_userns`, which has `audit deny capability,`. The next mount is refused:
   `apparmor="DENIED" operation="capable" profile="unprivileged_userns" comm="(python3)" capability=21
   capname="sys_admin"`.
3. **systemd then drops the mount sandbox without a word.** `setup_namespace()` reports the missing capability as
   `ENOANO`. Unless `insist_on_sandboxing()` is true (`:3487-3528`: temporary file systems, a root dir or image,
   bind mounts that move things, `DynamicUser=`, a log namespace), it logs only at debug level and carries on:
   `log_debug("Failed to set up namespace, assuming containerized execution and ignoring.")` (`:3964-3986`). That
   is the silent path for the whole `Protect*`/`Private*` file-system family. `TemporaryFileSystem=` is the
   "insist" case (226).
4. **The logged no-ops.** `PrivateNetwork=` → `log_notice(... proceeding without.)` (`:4655`). `PrivateIPC=` →
   `log_warning_errno(... ignoring: %m)` (`:4665`). `ProtectHostname=` → `log_warning(... ignoring namespace
   setup.)` (`:1969`). The hostname seccomp filter is then loaded at that early stage. INFERENCE: its
   `seccomp_load()` fails there, because there is no `CAP_SYS_ADMIN` and NNP isn't set yet, and
   `seccomp-util.c:2273-2278` skips it with `log_debug_errno(... skipping)`. That fits `Seccomp: 0` in n14.
5. **The capability failures.** Every option that shrinks the bounding set ends in
   `capability_bounding_set_drop()`. That needs `CAP_SETPCAP`, which the user manager lacks (`CapEff
   0000000800000000`, only `CAP_WAKE_ALARM`), so it fails with `EXIT_CAPABILITIES`: `log_error_errno(r, "Failed to
   drop capabilities: %m")` (`:6102-6107`). The kernel also logs `DENIED ... capname="setpcap"` where a user
   namespace was in place.

`execve` rule, `man systemd.exec` (259), SystemCallFilter=, says: "access to the execve() system call is required
for the execution of the service binary — if it is blocked service invocation will necessarily fail".

### 3. `AppArmorProfile=` in a user unit (dry run, no profile loaded)

`systemd-run --user -p AppArmorProfile=vase-s10-probe /usr/bin/gnucat ...` fails closed: **231/APPARMOR**,
`Failed to prepare AppArmor profile change to vase-s10-probe: No such file or directory`. The user manager does
call `aa_change_onexec()` (`exec-invoke.c:6211-6218`), and a missing profile stops the unit. So naming the profile
in the unit, not only by path attachment, gives a daemon that won't run unconfined if the profile isn't loaded.
Whether the change succeeds once the profile is loaded is case a8/a9 of the AppArmor half.

## AppArmor half: sudo steps for the owner

This half needs sudo twice. It loads one test profile into the kernel straight from the worktree: nothing is
written to `/etc/apparmor.d` or the parser cache, and nothing survives a reboot. It also installs two root-owned
copies of GNU coreutils binaries. Both are removed in the same sitting. Everything between the two sudo blocks runs
as you, with no sudo. Read `spikes/S10/apparmor/vase-s10-probe` first: it's 20 lines and allows only
`abstractions/base`, mapping its own binaries, reading `attr/current`, `/usr/lib/os-release` and one fifo. Run the
steps from a normal terminal on the desktop, with the dev shell closed:

```sh
cd /home/martin/src/vase-chained-wt/s10
cat /proc/loadavg                      # wait if the first number is over 40

# 0. Before (no sudo)
sh tools/before-after.sh snapshot ~/.cache/tiler-dev-snapshots/s10-aa-before.snap
sh spikes/S10/apparmor-probe.sh --check-gone      # expect: profile loaded: no, .../vase-s10: absent

# 1. Install (sudo): two root-owned test binaries, and the profile into the kernel only
sudo install -d -o root -g root -m 0755 /usr/local/libexec/vase-s10
sudo install -o root -g root -m 0755 /usr/bin/gnucat /usr/local/libexec/vase-s10/probe-cat
sudo install -o root -g root -m 0755 /usr/bin/gnuenv /usr/local/libexec/vase-s10/probe-env
sudo apparmor_parser --replace --skip-cache spikes/S10/apparmor/vase-s10-probe

# 2. Probe (no sudo): about 20 s, transient units only
sh spikes/S10/apparmor-probe.sh

# 3. Remove (sudo), in the same sitting, even if step 2 failed
sudo apparmor_parser --remove --skip-cache spikes/S10/apparmor/vase-s10-probe
sudo rm -r /usr/local/libexec/vase-s10

# 4. After (no sudo)
sh spikes/S10/apparmor-probe.sh --check-gone      # expect exit 0: profile loaded: no, absent, units left: 0
sh tools/before-after.sh snapshot ~/.cache/tiler-dev-snapshots/s10-aa-after.snap
sh tools/before-after.sh compare ~/.cache/tiler-dev-snapshots/s10-aa-before.snap \
  ~/.cache/tiler-dev-snapshots/s10-aa-after.snap
```

`/usr/local/libexec` already exists (root, 0755, empty), so step 3 leaves it as it was. The binaries are the GNU
ones (`gnucat`, `gnuenv`) because `/usr/bin/cat` here is rust-coreutils: one multicall binary, hardlinked 116
times, that picks the tool from `argv[0]`, so a copy named `probe-cat` wouldn't run as cat. If anything goes wrong
between steps 1 and 3, step 3 still undoes all of it, and a reboot drops the profile anyway.
