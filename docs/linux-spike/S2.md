# S2: the input contract of the prefix

Spike S2 of the Linux Tiler (docs/linux-tiler/wayfinder.md §5, M0b row 1). It feeds §3.3, round 2 (Q2.1, Q2.2) and the
engineering defaults. Levels: L3 first (three runs), then L1 (one run).

## Question

Does the map's prefix work as §3.3 describes it: Alt+A through `grab_accelerator`, `Main.pushModal` synchronously in
the accelerator handler, the next key taken by the grab, `popModal` on that key's release? And around it: the
Alt-release race, NONE vs NORMAL action modes, `notify::revoked`, the 3 s timeout, the kill chord inside the grab,
Super+L inside the prefix, what the focused app sees (a GTK4 app, Ghostty, an Xwayland client), and **a fast Alt+A
then `\` 5-10 ms apart into a GTK4 entry with IBus active: does anything land, and how long from press to effect?**
Also: can the shell see keys without a grab, do temporary accelerators work for the sticky keys, and does the nested
keyboard layout work despite the `this._xkbOptions is undefined` TypeError that S11 saw?

## Answer

**Yes, the contract holds.** In every run, at every gap down to 0 ms and with the main loop blocked, nothing from the
prefix landed in the GTK4 entry with IBus in the path, and `\` reached the grab actor in order. Alt+A to grab-up took a
median of 3-4 ms on the loaded host (the `pushModal` call itself 0.6 ms). Alt+A's own key event goes through IBus
first, and IBus hands keys back in order. NONE filters every binding, the kill chord included, so the grab handler has
to check the kill chord itself, and that works. Super+L reaches the prefix as `l` with Super. NORMAL lets GNOME's
bindings through. `revoked` works but is temporary. The 3 s timeout works. The shell cannot see any key without a
grab. Temporary accelerators work.

Four things change in the details, and one new risk comes up:

1. **Pop on the release of the key that ends the prefix: the command, Esc and the kill chord.** A pop on the press
   lets that key's release reach the app (GTK4 `key-released backslash`, X11 `KeyRelease backslash`). Esc and the kill
   chord popped on the press in this spike, and their releases leaked the same way.
2. **The kill-chord check must test `MOD4_MASK`, not `SUPER_MASK`.** Inside the grab, Super shows up as
   `MOD4_MASK` (0x40) in `get_state()`. `SUPER_MASK` was never set.
3. **Drop keys older than the prefix.** If a shell entry (the overview search) has key focus, IBus can return a key
   typed *before* Alt+A *after* the grab is up, and the prefix takes it as its command. In run 1 a `-` typed before
   Alt+A arrived 1.7 s late and was taken. The fix: allow the prefix in `NORMAL` only, and in the grab handler ignore
   any key whose event time is earlier than Alt+A's.
4. **Temporary accelerators need `TRIGGER_RELEASE`.** Without that flag the accelerated key's release reaches the
   app.

**New risk: X11 clients see an Alt press without a release.** At every prefix the Xwayland client (`xev`) got
`KeyPress Alt_L` and then nothing: no `FocusOut`, no `FocusIn`, no `KeyRelease Alt_L`. Later events carry the right
modifier state (0x0). But an X11 app or game that tracks raw key down/up can believe Alt is still held. GTK4 apps and
Ghostty get a real keyboard leave and enter instead. GTK4 windows go to backdrop for the length of the prefix.
Ghostty sends focus-out and focus-in reports (`CSI O`, `CSI I`) to the program inside it, so tmux or vim with focus
events on see a focus loss at every prefix.

**The nested keyboard layout works, by luck.** The TypeError comes from the `tiler-dev` mode having no keyboard
indicator in its panel. Because of it the shell never applies its own keymap, so mutter's built-in `us` keymap stays
in place. That is exactly the owner's only input source (F22). The keysyms were correct in all three clients.

**Nothing here blocks the architecture.** The X11 Alt problem and the terminal focus reports are behaviour to write
down or fix (S3 replay, or a Keymap note), not reasons to change the design.

## What it decides

**§3.3, the Prefix row: confirmed, with these rules added.**
- `pushModal` runs synchronously in `accelerator-activated`. No check like SwitcherPopup's for Alt already being
  released is needed: in the 0-5 ms and blocked cases Alt was already up when the grab went up (`altHeldAtArm` false),
  and the prefix doesn't depend on Alt being held.
- The prefix ends on the **release** of the key that ends it: the command, Esc, or the kill chord's Esc. The
  timeout, `revoked` and EOF end it at once.
- The grab handler checks the kill chord first, testing `CONTROL_MASK`, `MOD1_MASK` and `MOD4_MASK`, before any
  other key.
- The grab handler ignores (does not forward) any key whose `get_time_us()` is earlier than the Alt+A event's.
- Alt+A, Alt+E and the other chords are allowed in `Shell.ActionMode.NORMAL` only. With `OVERVIEW`, a shell search
  entry has key focus, and keys sent to IBus there can overtake the prefix.
- **`revoked` is temporary.** `is_revoked()` only means "another grab is on top" (`clutter-grab.c:128`). It flips
  back to false when that grab goes (`clutter-stage.c:3240`). The extension should therefore end the Prefix and the
  Overlay when `revoked` turns true, not wait for it to clear. That `popModal` of a revoked grab is safe is an
  INFERENCE from `main.js:840-855` (popping a grab that isn't the topmost); it wasn't run.
- Keys typed after the command but before its release (`q` and `z` in `keys-before-pop`) go to the grab. They are
  lost unless S3 shows replay works. That is the map's rule, now measured.

**§3.3, the Sticky row: the timer stays.** An event filter added by the extension and the stage's `captured-event`
saw **0 of 4** key events meant for a client, at L3 and at L1. mutter's filter is first in the list (`events.c:328`,
`clutter-event.c:1294` appends later ones) and stops the event once Wayland has it. So "any other key" can't end
Sticky: the 500 ms timer stays. Temporary accelerators work: Shift+Left fired and other keys still reached the app.
They must use `Meta.KeyBindingFlags.TRIGGER_RELEASE`, so mutter also takes the key's release
(`keybindings.c:1505-1510`; `accelerator-deactivated` fired, and no release reached GTK). Without the flag GTK got
`key-released Left` with no press before it.

**§3.3, the Overlay row (NORMAL): as the map says, with two consequences confirmed.**
- Inside a NORMAL grab:
  - the NON_MASKABLE kill-chord binding fires;
  - a NORMAL-allowed Super+L binding fires, so on the real session the screen would lock;
  - Alt+A's accelerator fires (`alt-a-while-armed`), so it has to be forwarded as a key, as the map says;
  - Alt+Tab opens the switcher. The switcher's own `pushModal` revokes the Overlay's grab, focus moves to another
    window, and the grab comes back un-revoked with the Overlay still armed.
- So "ends on a focus change" and "ends on `revoked`" are both needed.

**Q2.1 (Linux Keymap deviations): every item S2 can check holds.**
- The 3 s timeout: the grab dropped at 3002 ms, the client had the keyboard again 15-20 ms later, and the next key
  landed.
- Keys with no row are swallowed by the grab (unless S3 shows replay).
- Alt+A then Super+L reaches vase: the grab got `l` with `MOD4`, and the Super+L binding didn't fire.
- The kill chord works inside the NONE grab, inside a NORMAL grab and outside any grab.

Proposed **new Ubuntu notes** for the Keymap:
- "During a prefix the focused app loses the keyboard: GTK apps briefly show as inactive, and terminals report
  focus-out and focus-in to the program inside."
- "X11 apps see Alt pressed but not released at each prefix." Or fix this if S3 shows a replayed Alt release works:
  that becomes a K4 use case.

**Q2.2 (the picker auto-opens with NORMAL):** nothing in S2 argues against it. The Overlay's exit rules above (focus
change, `revoked`) are required, not optional.

**Engineering defaults and tests:**
- **Clutter virtual keyboard keys trigger `grab_accelerator` and `addKeybinding` bindings, at L1 and L3.** That is
  half of S3's first question, answered. L1 tests can drive the prefix with
  `seat.create_virtual_device(KEYBOARD_DEVICE)`, as this spike's `s2core.js` does.
- The L1 image has no `ibus`, so L1 covers the path without an input method. The IBus path is L3 only, unless
  `ibus` is added to `chained-tiler-test`.
- **The dev shell's mode** could add `"keyboard"` to its panel's right box, which would apply the shell's keymap
  properly. That changes a reviewed recipe, though, and isn't needed for this owner (mutter's default is `us`), so
  it is left as it is.

## Method

- **Spike code** is in `spikes/S2/`:
  - `extension/s2core.js` is the candidate prefix: `grab_accelerator('<Alt>a')` plus `allowKeybinding(NORMAL |
    OVERVIEW)`; `pushModal` in `accelerator-activated`; a 1x1 St catcher; `key-press-event` and `key-release-event`
    handlers; a 3 s timeout; Esc; the kill chord; a `notify::revoked` log.
  - It also adds a Super+L accelerator grabbed and allowed for NORMAL | OVERVIEW the way `shellDBus.js:322-337` does
    for gsd-media-keys (the nested shell has no gsd), and the kill chord as an `addKeybinding` NON_MASKABLE binding in
    `ActionMode.ALL` from a compiled schema.
  - Keys come from a Clutter virtual keyboard inside the shell, by evdev code.
  - Every record carries `GLib.get_monotonic_time()`, the clock Clutter stamps events with.
  - `extension/scenarios.js` holds the scenarios.
  - The probes:
    - `probe_gtk.py`, a GTK4 window with one `Gtk.Entry` that logs keys, focus, `is-active`, preedit and every text
      change on `CLOCK_MONOTONIC`, run with `WAYLAND_DEBUG=1`;
    - `bytelog.py`, run inside Ghostty in raw mode with focus reporting on;
    - `xev -event keyboard -event focus` through Xwayland.
  - `analyze.py` puts the four logs side by side per scenario.
- **L3** (`spikes/S2/run-l3.sh`): `tools/dev-shell.sh --x11`, unchanged and niced, between `tools/before-after.sh`
  snapshots.
  - The recipe loads only `vase-gnome/extension` of its checkout, so for each run that directory's contents were
    swapped for `spikes/S2/extension` and restored from git afterwards; the trap restores it on any exit.
  - The extension starts the three clients inside the nested shell, runs the scenarios against each, writes
    `$HOME/s2/shell.jsonl` (the run dir's HOME) and ends the shell with `global.context.terminate()`.
  - One devkit at a time; the script refuses if `mutter-devkit` runs and waits while the 1-minute load is 40 or more.
- **L1** (`spikes/S2/run-l1.sh`): `tools/linux/podman.sh l1`, unchanged, with `spikes/S2/l1/run.sh` swapped in for
  `vase-gnome/tests/l1/run.sh` and restored afterwards.
  - It runs `gnome-shell-test-tool --headless --extra-filter io.github.maartenhaine.S2Probe` on `spikes/S2/l1/s2.js`
    (same core and scenarios, the GTK4 probe, a perf-helper window to Alt+Tab to), under `dbus-run-session` and the
    mocked system bus, with no network.
- **Source:** mutter 50.1 from `gitlab.gnome.org/GNOME/mutter/-/raw/50.1/` (clutter-input-method.c,
  clutter-input-focus.c, clutter-grab.c, clutter-stage.c, clutter-event.c, meta-wayland-text-input.c,
  meta-seat-native.c), the map's copies of events.c and keybindings.c, and gnome-shell 50.1's JS extracted from the
  installed `libshell-18.so`.

**Host, every run:** Ubuntu 26.04, gnome-shell 50.1-0ubuntu1.5, libmutter-18-0 and mutter-dev-bin 50.1-0ubuntu2.5,
ibus 1.5.34~rc2, GTK 4.22.4, Xwayland 24.1.10. The 1-minute load was 20-45 throughout, and the nested shell ran at
nice 19. **Times are therefore pessimistic, and their maxima are host load, not the design.**

### Fast Alt+A then `\` into a GTK4 entry with IBus

- **IBus was in the path.** `Main.inputMethod._context` was set, the input source was `xkb:us` (engine `xkb:us::eng`),
  and the probe's text-input was enabled (`zwp_text_input_v3.enable` after each enter). The Alt+A key event that fired
  the accelerator carried `FLAG_INPUT_METHOD` in **18 of 18** GTK prefixes and **4 of 4** Ghostty ones: IBus had the
  key first, and mutter ran the keybinding on the copy IBus handed back. It was never set for xev (**0 of 4**: an
  X11 client has no text-input).
- **The order is safe by construction.** The flow:
  - a key for a client with text-input goes to the input method before keybindings (`events.c:168-171` before
    `:256-257`);
  - gnome-shell sends it to IBus asynchronously and stops it (`inputMethod.js:344-360`);
  - the copy comes back flagged (`clutter-input-method.c:336-350`) and skips the input method the second time
    (`:460`);
  - so the copy reaches keybindings, Alt+A's accelerator fires and the grab goes up before the next key's copy is
    handled;
  - mutter relies on IBus answering in order ("we rely on the IM implementation to notify back of key events in the
    exact same order", `:336`).
- **The scenarios.** Alt↓ (30 ms), then a↓ at 0, a↑ at g/3, Alt↑ at 2g/3 and `\`↓ at g, then `\`↑ 40 ms later:
  - with GLib timeouts, g = 0 (all four in one main-loop turn), 2, 5, 10 and 20 ms;
  - spun with the main loop blocked, g = 5 and 10 ms.

Run 2, GTK4 target. Run 3 gave the same results.

### The Alt-release race

`altHeldAtArm` (`global.get_pointer()` mods right after `pushModal`) was false at g = 0, 2 and 5 ms and in both
blocked cases, and true at 10 and 20 ms. In every case the a↑, Alt↑ and `\` that followed went to the grab actor in
order, and the prefix worked. SwitcherPopup's check (`switcherPopup.js:144-156`) matters only to a mode that needs Alt
held; the prefix doesn't.

### NONE vs NORMAL, the kill chord and Super+L

Run 2 at L3, the same at L1.

| Scenario | What fired | What the grab actor got |
|---|---|---|
| Kill chord, no grab | the `addKeybinding` NON_MASKABLE binding | – |
| Kill chord, NONE grab | **no binding** | Ctrl, Super, Alt, then Esc with state `0x4c` (CONTROL 0x4, MOD1 0x8, MOD4 0x40; `SUPER_MASK` 0x4000000 not set). It popped (`kill-chord-in-grab`) |
| Kill chord, NORMAL grab | the binding (ActionMode.ALL), which popped the grab (`kill-binding`) | the modifiers only |
| Super+L, no grab | the Super+L accelerator | – |

`keybindings.c:1465-1466` treats a filtered binding as no binding (F14).

### `notify::revoked`

- A second `pushModal` (SYSTEM_MODAL) on top of the prefix made our grab notify `revoked: true`, and that modal's actor
  got the next key (`x`).
- `popModal` of that second grab made ours notify `revoked: false`, and the next key (`\`) came back to the prefix.
- The same at L1. See the source lines in "What it decides".

### The 3 s timeout and Esc

- `timeout`: popped at **3002.5 ms** (L3 runs 2 and 3, and L1: 3002.53, 3002.52, 3002.51). `wl_keyboard.enter` reached GTK at
  3017 ms, and `y` typed at 3383 ms landed.
- `escape`: popped on Esc's press, and GTK then got `key-released Escape` with no press (the release leak behind
  rule 1).

| Client | At Alt+A | During the grab | At the pop |
|---|---|---|---|
| GTK4 (`probe_gtk.py`) | `key-pressed Alt_L` (Alt reaches the app before `a` triggers the accelerator) | `wl_keyboard.leave`, text-input leave and disable; `focus-leave` and **`is-active` false** (backdrop) | `wl_keyboard.enter` and `modifiers`, text-input enter and enable, `is-active` true; after a pop on the **press**, also `key-released backslash` with no press |

### Watching keys without a grab

`Clutter.Event.add_filter(global.stage, …)` and `global.stage` `captured-event` around two taps of `z` into GTK4:
**`filterKeys` 0, `capturedKeys` 0** (L3 runs 2 and 3, and L1), while the probe got both `z`s.

In run 1, with the overview's search entry focused, the same filter saw 6 events and `captured-event` 4. The shell
sees keys only when one of its own actors has key focus.

### The IBus ordering hazard with a shell entry (run 1)

- The overview was open, so the overview's search entry (an St entry) had key focus. A St entry offers keys to the
  input method after the keybindings, so Alt+A's accelerator fired straight away (`im: false`), while the keys typed
  before it were still out at IBus. That IBus took up to 1.7 s is host load.
- The result: `prefix-slow` took `-` (typed in the baseline before Alt+A) as its command: `grab-press sym=0x2d im=True
  lag=1715095us`, 173 µs after the grab went up.
- With a Wayland client focused (runs 2 and 3) this can't happen: Alt+A itself goes through IBus in order. Hence the
  "NORMAL only" and "drop keys older than Alt+A" rules.

### The nested keymap and the `_xkbOptions` TypeError

- **The chain:**
  - `KeyboardManager._xkbOptions` is set only through `setKeyboardOptions()`. At startup that happens in
    `InputSourceManager.reload()` (`keyboard.js:392`), whose only caller there is the panel's keyboard indicator
    (`InputSourceIndicator`, `keyboard.js:906`, `panel.js:424`).
  - The `tiler-dev` mode's panel has `"right": []` (`tools/dev-shell.sh:172`), so the indicator, and `reload()`, never
    run.
  - IBus's ready signal then activates the `us` source; `apply()` runs `_buildOptionsString()`, which throws
    (`keyboardManager.js:207-208`).
  - `apply()` catches it with `.catch(logError)` (`keyboardManager.js:125-127`), so `activateInputSource` goes on:
    the IBus engine is set and `currentSource` is `us`. The CRITICAL came three times in each of the good runs.
- **The effect:** the shell never sets a keymap (`currentKeymap` null, `xkbOptions` `undefined` at start and end of
  every L3 run), so mutter's own default stays: `meta_keymap_description_new_from_rules (NULL, "us", …)`
  (`meta-seat-native.c:242-247`).
- **Keys still type correctly.** Evdev 45, 43 and 12 typed `x`, `\` and `-` in GTK4 (`changed='x\\-'`), Ghostty
  (`'x'`, `'\\'`, `'-'`) and xev (`keysym 0x78, x`, `0x5c, backslash`, `0x2d, minus`).
- **L1 is the control.** The test tool runs the `user` mode, whose panel has `keyboard` (`sessionMode.js:67,81`).
  There `xkbOptions` was `[]`, the keymap `us,us` / `pc105+inet`, and no TypeError.
- **So:** an L3 key result is trustworthy for a `us` keyboard with no xkb options, which is this owner's only
  setup.

### The host was left alone

`tools/before-after.sh compare`: **"no watched item changed"** after each of the three L3 runs (`compare.txt` in each
results dir); LockedHint `no`, no crash marker, the same `org.gnome.Shell` owner (pid 5222), no leftover
`TILER_DEV_RUN` processes, and `/var/crash` gained nothing from these runs. A
`/var/crash/_usr_bin_python3.14.1000.crash` dated 04:57:36 was there before the first run (05:02) and isn't from S2.
`vase-gnome/extension` and `vase-gnome/tests/l1/run.sh` were back at their committed contents after every run.

Xwayland in the nested shell (`--x11`) used display `:2`, with its socket in the shared `/tmp/.X11-unix` as the recipe
documents, and it was gone after the run.

## Limits

- **The keys came from a virtual keyboard.** They were a Clutter virtual keyboard inside the nested shell, not the
  devkit viewer's libei path and not a physical keyboard. All three enter the same seat and event path (the virtual
  device goes through the input thread like libinput), but the owner's feel check at L3 (M1c) is still the test for
  real typing.
- **The host was loaded** (load 20-45, nice 19), so the maxima are noise. The medians are upper bounds.
- **IBus ran only with the `xkb:us::eng` engine,** which passes every key back. An engine that commits text (CJK,
  compose) isn't in the owner's setup (F22) and wasn't tested.
