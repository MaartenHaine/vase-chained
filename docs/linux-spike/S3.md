# S3: virtual input against the prefix grab, and replay

Spike S3 of the Linux Tiler (docs/linux-tiler/wayfinder.md §5, M0b row 2). It feeds seam K4, round 2 (Q2.1, Q2.2),
the key-ownership state machine (§3.3) and the L1 test design.

## Question

1. Do Clutter virtual-keyboard keys trigger `grab_accelerator` bindings, so that L1 tests can drive the Tiler's keys
   from inside the shell?
2. Can a PassThrough key, or one Alt+A ("Alt+A, then Alt+A: send one Alt+A"), be replayed to the app after `popModal`
   without re-arming the prefix?
3. Can a click taken by a grab be replayed with a virtual pointer?

## Answer

**Yes to all three, with three rules.**

1. Virtual keys go through exactly the path physical keys take. A virtual Alt+A fires the `grab_accelerator`
   binding, and a virtual Ctrl+Super+Alt+Esc fires an `addKeybinding` NON_MASKABLE binding. The callback's device is
   the virtual device. So L1 can drive every key test from the automation script.
2. A PassThrough key replayed through a second virtual keyboard right after `popModal` reached the app 50 times out
   of 50 on Wayland and 50 out of 50 through Xwayland, over five runs. The app got its keyboard focus back before the
   key. A replayed Alt+A **does** re-arm the prefix if the binding is live. Three ways stop that, and all three
   delivered Alt+A to the app and left Alt+A arming afterwards:
   - a one-shot `filter-keybinding` handler (recommended);
   - `Main.wm.allowKeybinding(name, NONE)` for the duration of the replay;
   - ungrab, replay, then grab again.
3. A click taken by an overlay grab, replayed through a second virtual pointer after `popModal`, reached the window
   under the pointer 50 out of 50 times on each client.

The rules, all from mutter's seat being shared by every device (real and virtual):
- **Replay a key or a button only after the user has released it.** A replayed press of a key that is still
  physically down is dropped. The user's later release then reaches the app alone (K3a, P3). So the prefix pops only
  when the command key *and every other key pressed under the grab* are up (K3b). An overlay pops on the button's
  release, not its press.
- **A replayed key carries the modifiers held at replay time**, not the ones it was typed with. The xkb state is one
  per seat. For "hold Alt, tap A twice" that is exactly right: the app gets Alt+a.
- **A replayed chord that is one of the Tiler's own accelerators must be let through the binding filter for that one
  event.** The accelerator callback can't pass a key on: `handle_external_grab` returns nothing and `process_event`
  returns STOP after it runs.

Replay costs a median of 1.5 to 3.4 ms on Wayland and 8 to 12 ms through Xwayland (worst 23 ms), measured from the
replay call to the client's handler. That was headless, on llvmpipe, at nice 19, with the host's load at 30 to 47.

## What it decides

- **K4 (`Backend::send_key`) is viable.** Seam K4 goes ahead in M1c as planned. The extension owns one virtual
  keyboard and one virtual pointer, created in `enable()` and dropped in `disable()`. Disposing a virtual device
  releases anything it still holds (`release_device_in_impl`).
- **Q2.1, round 2:** two of the eight proposed Linux deviations go away.
  - "A key with no row after either prefix is swallowed" is dropped. Keys pass through as the Keymap says today
    (`14-retire/docs/keymap.md:70`).
  - "Alt+A, then Alt+A" sends one Alt+A by replay. That is no deviation either.

  The other six stand (S2 confirms them).
- **Q2.2, round 2:** with auto-open kept, a click outside the picker closes it *and* is replayed to what it hit. Two
  caveats go into the Keymap note:
  - the click lands where the pointer is at replay time, a few ms later;
  - it is replayed on release, so a drag that starts outside the picker becomes a click.
- **§3.3 Prefix row, "keys taken in flight":** replay, not drop. The rules:
  - the grab ends on the command key's release *and* when no key pressed under the grab is still down (a held key
    is waited for; the 3 s timeout still applies);
  - then the extension calls `popModal` and replays the PassThrough keys in order through its virtual keyboard;
  - a replayed key that matches one of its own accelerators (SendPrefix) is let through by a one-shot
    `filter-keybinding` handler for that press and its release, with a 100 ms fallback reset.
- **§3.3 Overlay row:** a click outside is forwarded to the daemon *and* replayed after the pop, on the button's
  release.
- **Engineering default, the replay filter:** a second handler on `global.window_manager` `filter-keybinding`. It
  returns true for the Tiler's own binding name while a pass count is above zero, and false otherwise. It is
  preferred over the other two because:
  - it is an exact fence: it sees the replayed press and release go by (`filterSeen: kept, passed, passed`);
  - it doesn't touch the shell's `_allowedKeybindings`;
  - it doesn't churn the grab. A regrab returns a new action id and binding name (129 → 131) that has to be
    re-allowed, and a real Alt+A pressed during the gap goes to the app.

  `allowKeybinding` stays as the fallback if a reviewer objects to the extra handler.
- **L1 test design (M1b/M1c and the CI suite):**
  - Keys are driven with `seat.create_virtual_device(KEYBOARD_DEVICE)` and `notify_key(time, evdev code, state)`, by
    keycode (matching F22). Clicks use a `POINTER_DEVICE`, with `notify_absolute_motion` then `notify_button`.
  - **Two devices per kind.** One stands for the user, the other is the extension's replay device. They share the
    seat state just as a real keyboard and the extension's device will, so the press-count and modifier rules are
    exercised for real.
  - A virtual device has no getter for the `ClutterInputDevice` its events carry. Tests map them through the seat's
    `device-added` signal, which comes in creation order.
  - **Create devices inside `run()`**, not at module import (see the flake below).
  - **Before any pointer test, move the pointer off (0,0).** A fresh pointer starts on the hot corner's pressure
    barrier: its first absolute motion to (500,350) ended at (0,350) and opened the overview (P1 in
    `spikes/S3/out/run4-hotcorner.log`). `warp_pointer` from there also stayed at x=0 but cleared the corner. Better:
    turn hot corners off in the test keyfile.
  - Hide the overview at the start, as `hello.js` does.
  - The Xwayland client has to be a window whose `WM_CLASS` is known, because the test tool's
    `MUTTER_WM_CLASS_FILTER` drops every other X11 window. GTK4 on X11 was dropped this way. `x11client.py` (plain
    ctypes Xlib, class `S3client`, passed with `--extra-filter`) works.
- **For the audit (round 3, Q3.4) and the M0a tripwires:** a virtual keyboard can type into any app. Two things
  follow:
  - Condition 3 gains "creates one virtual keyboard and one virtual pointer, and injects only keys and clicks its own
    grab took from the user";
  - the tripwire list gains `create_virtual_device` and `notify_key`/`notify_button` outside the one reviewed
    function.

  This is the same power gnome-shell's own on-screen keyboard uses (`js/ui/keyboard.js:1973,2111-2116`).

**Nothing here blocks the architecture.** One thing to fix in the L1 harness before CI depends on it:

- **The L1 shell sometimes never finishes starting.** In 5 of 12 runs, `GNOME Shell started` was never logged.
  `Scripting.runPerfScript` never saw the perf helper on the bus, the script never ran, and the run ended at the
  timeout (exit 124).
  - In the one hung run with a full log (`out/run12-startup-hang.log`), Xwayland had already started during startup.
    In the passing runs it started later, on demand.
  - The first four hangs had the virtual devices created at import time; the last one did not. So that was not the
    cause.
  - INFERENCE: this is a startup race in the headless shell under load, not something S3 does. The M0a hello test
    takes the same startup path, so it can flake the same way.
  - For now: a short timeout and one retry in `tools/linux/podman.sh l1`. A spike or an M1b task should find the
    cause before the L1 suite gates CI. It is UNVERIFIED whether the hello test hangs too.

Side observations for other spikes:
- **S2 (games):** under a stage grab, the bare Xlib client saw no `FocusOut`/`FocusIn`, only pointer `LeaveNotify`
  and `EnterNotify`. The Wayland client saw `wl_keyboard` leave and enter (GTK `focus-leave`/`focus-enter`).
  INFERENCE: Xwayland doesn't turn the grab into X focus events. What a real game does is still S2's and M6's
  question.
- **Orphan releases:** when the Alt+A accelerator fires, the app still gets the release of `a` (with Alt) on Wayland,
  because a `grab_accelerator` binding has no `release_pending` and an unmatched release propagates
  (`keybindings.c:1475-1497`). Apps already see this from every GNOME shortcut. The Xlib client got no such release.
- **The kill chord, as F14 says:** inside a NONE grab, a NON_MASKABLE `addKeybinding` chord did not fire, and the grab
  actor got Ctrl, Super, Alt and Esc (KC-none). The grab handler has to check for it.
- **O1 and N1:** Alt+A inside a NORMAL grab fires the accelerator, and the grab actor gets only the Alt press and the
  releases. Inside a NONE grab it doesn't fire, and the grab actor gets all four events. This matches §3.3's Overlay
  row ("forwarded as a key") only if the overlay forwards the accelerator callback to the daemon as a key. The grab
  actor alone never sees the `a` press.

## Method

**Level:** L1 only. A headless GNOME Shell 50.1 (`mutter 50.1`, MetaSeatNative) ran in `chained-tiler-test` (image
`localhost/chained-tiler-test:0f162fbd9318eba8`, packages from the 2026-11-06 archive snapshot). It ran through
`tools/linux/podman.sh spike S3`, a new subcommand with the `l1` rules: `--rm`, `--network=none`, `--cap-drop=all`,
`no-new-privileges`, the checkout mounted read-only, nice 19. Inside it, `spikes/S3/l1.sh` runs
`gnome-shell-test-tool --headless --disable-animations` under `dbus-run-session` and the L1 harness's dbusmock
system bus. Every run waited until the 1-minute load was under 40.

**The automation script** (`spikes/S3/s3.js`) plays the extension's part itself, so no extension is installed:
- `global.display.grab_accelerator('<Alt>a')`, `Main.wm.allowKeybinding(name, NORMAL)`, and `accelerator-activated`;
- the accelerator callback calls `Main.pushModal(actor, {actionMode: NONE})` synchronously;
- a 1×1 `St.Widget` grab actor records every key and button it gets, with its source device;
- `Main.wm.addKeybinding('s3-kill', …, NON_MASKABLE, ALL)` from a schema compiled in the container
  (`spikes/S3/schemas`).

It drives four virtual devices: keyboards P (the user) and R (replay), and pointers ptrP and ptrR.

**The clients** log every event with `CLOCK_MONOTONIC` times to one JSON-lines file:
- `spikes/S3/client.js`: GTK4 on Wayland, a capture-phase key controller, a click gesture, focus and crossing;
- `spikes/S3/x11client.py`: bare Xlib through Xwayland.

The same suite runs against each.

**The cases**, each recorded rather than asserted:

| Case | What happens |
|---|---|
| K1 | P types Alt+A with the client focused: does the accelerator fire, from which device, and what does the client see? |
| K2 ×10 | Alt+A arms; P types `x`; on its release the script pops and R replays `x`. Delivery and latency. |
| K3a | Alt+A arms; P presses `\`, then `x`, then releases `\`; the script pops and replays `x` at once, while P's `x` is still down. |
| K3b | The same, but the pop waits until no key pressed under the grab is down (`x` released). |
| K4 | P holds Alt and taps A twice. The second A arrives in the grab; on its release the script pops and R replays Alt+A. Strategies: `naive` (the binding is live), `allow` (`allowKeybinding` NONE), `filter` (one-shot `filter-keybinding` handler, with Alt held and with Alt released first), `regrab`. Afterwards, P's Alt+A must still arm. |
| O1, N1 | P types Alt+A inside a NORMAL grab and inside a NONE grab. |
| KC | P types Ctrl+Super+Alt+Esc with no grab, then inside a NONE grab. |
| P1, P1b | A virtual click on the client's centre. |
| P2 ×10 | An overlay (NORMAL) grab is up; ptrP clicks the client; on the release the script pops and ptrR replays press and release. |
| P3 | The same, but popping and replaying on the press, while ptrP's button is still down. |

### Source

Mutter and gnome-shell 50.1, from https://gitlab.gnome.org/GNOME/mutter/-/raw/50.1/ and
https://gitlab.gnome.org/GNOME/gnome-shell/-/raw/50.1/:

- **Virtual keys take the physical path.**
  - `meta-virtual-input-device-native.c:394-464`: `notify_key` runs `notify_key_in_impl` on the input thread, which
    calls the same `meta_seat_impl_notify_key_in_impl` that libinput keys use, with the virtual device as the event's
    device.
  - `meta-seat-impl.c:580-665`: that function builds the event from the seat's one `xkb` state and queues it to the
    main thread (`queue_event` → `_clutter_event_push`, `:409-425`). No synthetic flag is set.
  - `events.c:122-326`, `meta_display_handle_event`: it checks the source device only for tablets. Keys go to
    `meta_keybindings_process_event` before Wayland (`:274-276`), as F4 says.
- **Why a replayed press of a held key is dropped.** The press count is per seat, not per device:
  `meta-seat-impl.c:596-607` for keys and `:1007-1016` for buttons. The virtual device keeps its own count as well
  (`meta-virtual-input-device-native.c:413-421`).
- **Why an accelerator can't pass a key on.** `keybindings.c:1421-1515`: once a binding matches and is not filtered,
  the handler runs and `process_event` returns STOP (`:1503-1514`). `handle_external_grab` returns nothing
  (`:1257-1268`). The filter runs first: `meta_compositor_filter_keybinding` at `:1461-1465` leads to `not_found`,
  which returns FALSE, so the key goes on to Wayland.
- **The filter signal.** gnome-shell `src/shell-wm.c:158-165`: `filter-keybinding` has the
  `g_signal_accumulator_true_handled` accumulator, so a second handler runs when the shell's own returns false, and a
  true stops emission. The shell's handler is `windowManager.js:1589-1602`.
- **The device in the callback.** `accelerator-activated` carries the event's source device (`display.c:305-310`,
  `:2223-2231`). That tells a replayed Alt+A apart, but it can't un-consume the key.
- **Why the app has its focus back before the replayed key.**
  - `popModal` → `grab.dismiss()` (`main.js:762`) → the stage's `is-grabbed` notify → `meta_wayland_input_sync_focus`,
    synchronously (`meta-wayland-input.c:56-59,257-264`) → `wl_keyboard.enter` with the pressed keys and the
    modifiers (`meta-wayland-keyboard.c:706-714`);
  - the replayed key comes later, through the input thread.
- **Shortcut inhibition is checked per source device** (`keybindings.c:1452-1459` passes it to
  `meta_window_shortcuts_inhibited`). An inhibiting client wasn't tested here. M1c's "a shortcut-inhibiting client
  cannot mask the kill chord" needs its own L1 client (GTK `inhibit_system_shortcuts` and the shell's permission
  dialog).
